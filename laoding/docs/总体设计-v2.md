# 第一层 · 三个角色

## 1. 系统是什么

### 1.1 一句话定位

**一个 3/4 俯视的像素风校园地图，玩家在地图上走，遇到三个有记忆、有性格、会自己走动的智能体，靠"跟人说话"而不是"点菜单"来获取校园信息。**

北京交通大学在校生校园项目，课程设计。目标是做一个"AI 万事通"，但**不能是又一个聊天框**——单纯问答只能保证 80 分。

### 1.2 关键指标

| 指标 | 数值 |
|---|---|
| 世界尺寸 | 5208 × 2930 世界像素 |
| 智能体数量 | 4 个（**3 个社交型 + 1 个地图向导**，正文主线讲三个社交型） |
| 社交网络边数 | 2 条（链式，路径唯一） |
| 校园图谱规模 | 约 180 节点 / 200 条三元组 / 10 类边，**两跳遍历**（§4.6） |
| NPC 之间每天交流 | ≤ 6 次（4 小时一段，每段最多一次） |
| 并发用户规模 | 50 个独立会话（社交模式下例外，见 §20） |
| 每日 LLM 成本 | 约 0.5~0.8 元（50 人全量放开，含真社交，估算） |
| 月度 LLM 成本 | 30 元以内 |
| 意图缓存命中率 | 目标 70%+ |
| 按时缓存命中率 | 约 20% |
| 云端 GPU 花费 | 开发期 + 答辩合计约 60 元 |

### 1.3 三个角色，五块功能

**这是全文档的总纲**：系统的每一项功能都不是一个页面，而是**某个人会的一门手艺**。

| 功能 | 载体 | 玩家怎么触发 | 输入 | 输出 | 数据文件 | 负责人 |
|---|---|---|---|---|---|---|
| **校园信息库 + AI 问答** | 学长 · 甲 | 走到他面前说话 | 自然语言问题 | 口语回答 | `knowledge.json`（800 条切片） | 1 号 + 2 号 |
| **图谱关系问答** | 学长 · 甲 | 同上（问"怎么办事") | 同上 | **一条可解释的路径** | `campus_kg.json`（200 条三元组） | 五人分摊 |
| **众包口碑** | 阿姨 · 丙 | 走到窗口前说话 | 打分 + 评语 | 时间衰减加权评分 + 榜单 | `reviews.json` | 3 号 |
| **失物招领** | 保安 · 老丁 | 呼叫他 / 走过去说 | 文字描述 **or 一张照片** | 候选失物 + 捡到地点 | `lostitems.json` | 4 号 |
| **报修** | 保安 · 老丁 | 走过去说话 | 地点 + 问题 | 工单条目，他人可查 | 保卫处公共层 | 4 号 |

> **地图导航与带路**由向导 · 小北承载——他属于地图层，是**地图的附庸**（只做带路 / 导航 / 定位，不涉及其他功能、不参与社交），详见 **§8**。

### 1.4 差异化策略：分数预期

| 层次 | 做法 | 分数预期 |
|---|---|---|
| **保底** | 校园信息库 + AI 问答 + 口碑 + 失物招领 | 80 |
| **冲高** | 多智能体社交网络（§14–§16）+ 主动性（§13） | 90+ |
| **加分** | 云端 CV 以图搜物、像素地图底座 | 展示分 |
| **附加（可裁剪）** | 社交模式 + 真实坐标映射，见 **§20** | 展示分 |

> 前三行是主线，**必须交**；最后一行是附加功能，**不做也能交**。§20 依赖主线，主线不依赖 §20。

### 1.5 硬约束（不可违反）

1. **单文件交付**：全部前端在一个 HTML 里，零依赖、零构建
2. **思源楼尺寸冻结**：作为标尺基准，不得调整
3. **道路不硬归两档**：按实测宽度分级（`W >= 100` → 大路，`W < 100` → 小路）
4. **5 个缺口即校门**：PPT 边界线上的 5 处缺口一律按校门处理
5. **不引入后端**（云端 CV 走无状态代理，不算后端服务）

> **唯一的条件性例外**：§20 的社交模式在**开启时**需要一个位置服务进程（约 30 行）与 HTTPS 环境。默认关闭，主线不受影响。

## 2. 核心机制：功能 = 智能体 = 工具集 + 人格配置

这是整个架构的枢纽，也是三个角色得以成立的原因。

### 2.1 系统分四层

```
┌──────────────────────────────────────────────────────────────┐
│ 会话层    50 份互相不可见的会话                                │
│           各自的位置 / 私密记忆 / 对话历史 / 信箱               │
└──────────────────────────────────────────────────────────────┘
                              │ 读/写
┌──────────────────────────────────────────────────────────────┐
│ 智能体层  向导·小北 │ 学长·甲 │ 阿姨·丙 │ 保安·老丁            │
│           └── 共用引擎：记忆检索 · 意图分类 · 工具调度 ·        │
│                        模板生成 · 主动引擎 · 气泡渲染 ──┘      │
└──────────────────────────────────────────────────────────────┘
                              │ 调用
┌──────────────────────────────────────────────────────────────┐
│ 能力层    MapAPI.focus()  searchKnowledge()  getRating()      │
│           pathTo()        askLLM()           listWindows()    │
│           walkGraph()     matchLostItem()    matchByImage()【云端】│
│           reportRepair()                                      │
└──────────────────────────────────────────────────────────────┘
                              │ 读写
┌──────────────────────────────────────────────────────────────┐
│ 数据层    campus.json · knowledge.json · campus_kg.json       │
│           lostitems.json · reviews.json · 4 份人格配置         │
│           world · publicMemory · player_<id> · inbox          │
└──────────────────────────────────────────────────────────────┘
```

### 2.2 引擎只有一份，其余人填配置

**"失物招领"不是一个页面，而是保安老丁会的一门手艺。**

```json
{
  "id": "guard",
  "name": "保安 · 老丁",
  "role": "保卫处值班",
  "persona": "公文腔，只讲流程，不寒暄",
  "tools": ["matchLostItem", "matchByImage", "reportRepair"],
  "unknown_line": "这个不归我们管，你去找教务处。"
}
```

引擎读 `tools` 决定这个人会干什么，读 `persona` 决定他怎么说话。

**收益**：玩家不需要知道"功能菜单在哪"，他只需要**走到这个人面前说话**。换一个功能，只换一份配置，**引擎一行代码不改**。

### 2.3 目录结构

```

data/
  campus.json                地图与建筑坐标
  knowledge.json             校园信息库（800 条切片）
  campus_kg.json             校园图谱（200 条三元组）
  lostitems.json             失物条目
  reviews.json               口碑数据
  agents/
    guide.json               向导（组长）
    senior.json              学长（甲）
    auntie.json              阿姨（丙）
    guard.json               保安（丁）
cloud/
  proxy.js                   云函数代理，约 30 行
  cv_service.py              CLIP FastAPI，跑在按需 GPU 上
```

## 3. 记忆与认知边界：三个角色共同的地基

三个角色的功能都建在同一套记忆上——学长记得你说过什么、阿姨记得你常来、保安记得谁丢了什么。

### 3.1 记忆分两层，这是多用户架构的地基

| 层 | 谁可见 | 内容 |
|---|---|---|
| **公共层**（`visibility: "public"`） | 所有人 | 智能体互相社交写入的信息、世界事件、他人的足迹与点评 |
| **私密层**（`visibility: "private"`） | 仅该 `playerId` | 玩家跟某个智能体说过的私人信息 |

条目结构：

```json
{
  "desc": "玩家 A 说他要考本校研究生",
  "time": "2026-09-20 14:30",
  "importance": 7,
  "visibility": "private",
  "playerId": "u_8f3a2c",
  "source": "玩家 A"
}
```

> **`visibility` 和 `playerId` 这两个字段现在就要留**，否则后期接多用户等于重做引擎。

检索规则：`visibility === 'public' || playerId === 当前玩家`。

### 3.2 认知边界：他不是不肯说，是真的不知道

智能体只认得自己感知过的世界。**"我不知道"比"答对了"更有说服力。**

```json
"knows":   ["选课", "绩点", "社团", "考研", "转专业"],
"refuses": ["失物招领", "食堂评分"],
"unknown_line": "这个我真不知道，你去问问保卫处吧。"
```

`refuses` + `unknown_line` 是人格配置里**最有价值的两个字段**。

**`knows` 在图谱上落在哪**（见 §4.5）：字符串数组的含义不变，映射时对图谱节点名与 `alias` 做一次**别称解析**即可。

**`knows` 里没有的，就是 §16 表里"图上有、他没记住"那一行**——`unknown_line` 因此不是敷衍，是设定。

> 5 个人已经写好的人格配置**一个字都不用改**。

## 4. 学长 · 甲 —— 校园信息库与 AI 问答

> 系统的**知识入口**。玩家想知道"怎么办事"，最后都落到他这儿。

### 4.1 他管什么

| 项 | 内容 |
|---|---|
| 角色 | 大三 · 计算机 |
| 工具 | `searchKnowledge` + `askLLM` + `walkGraph` |
| 知道 | 选课 / 绩点 / 社团 / 考研 / 转专业 |
| 拒绝 | **失物招领 / 食堂评分**（会把你推给保卫处） |
| 问候 | "哟，新来的？有事儿问我。" |
| 答不了时 | "这个我真不知道，你去问问保卫处吧。" |

玩家问失物招领他不装作知道，直接推给保卫处——**他的可信度来自他有边界**。

### 4.2 数据从哪来：不做爬虫

| | 判断 |
|---|---|
| **合规** | 爬教务系统违反使用条款，答辩被问到很难圆 |
| **成本** | 需要登录态 + 验证码 + 反爬对抗，一个人做不完 |
| **收益** | 校园信息是低频静态数据，爬一次管一学期 |

**替代方案**：把公开页面的文本丢给 LLM，让它输出 JSON，人工校对后存进 `knowledge.json`。这是一次性的数据工程，跑一次就不管了——**比爬虫稳、比爬虫快、还不违规**。

### 4.3 文本检索打底：倒排索引就够

**数据量测算**：建筑约 30 条 + 课程几百条 + FAQ 几百条 ≈ **800 条**。

用倒排索引 50 行 JS 就够，而且**命中率比向量还高**——校园词太专有（"思源楼""二食堂三楼""绩点换算"），语义向量反而会把它们模糊掉。

**但一定要保留 RAG 的骨架**：

1. **检索**：关键词加权 → 打分 → 取 top-3 片段
2. **增强**：把 top-3 拼进 system prompt
3. **生成**：LLM 只依据片段回答，禁止编造

**答辩话术**：

> 我们实现了检索增强生成。考虑到语料不到千条且专有名词密集，用基于关键词加权的稀疏检索替代稠密向量检索，免去了嵌入模型和向量库的依赖，同时把幻觉率压到最低。

只有一种问法真需要语义理解：**"有没有那种能安静自习的地方"**。用**标签 + 同义词表**覆盖即可——给地点打 `安静 / 有插座 / 可通宵` 标签，不用上模型。

### 4.4 但文本切片答不了三类问题

上面那套（倒排索引 → top-3 片段 → 拼提示词）能回答「二食堂几点关门」，因为答案**就在某一片文本里**。它答不了的是**答案散在多片文本之间**的那一类：

| 类型 | 例子 | 为什么切片答不了 |
|---|---|---|
| **路径型** | 「从思源楼怎么去二食堂」 | 两个地点各在一篇里，**"中间怎么走"不在任何一篇里** |
| **归属型** | 「计算机学院在哪个楼」「那我去哪儿开证明」 | 要走 学院→楼→楼里设的部门，**三段拼接** |
| **条件型** | 「办校园卡要带什么、几点去」 | 流程→材料×3 + 流程→办理地点→开放时段，**四片拼一段** |

这类问题的共同点：**答案是"关系"，不是"相似"**。

向量检索找的是"这段文本和问题像不像"；这三类问法的正确答案，是"这两个实体之间隔着一条什么路"。**路可以画出来，相似度不能。**

### 4.5 所以给他一张校园的图

**不给 NPC 用向量，给它们一张校园的图。** 六类节点、十类边，量级如下（全部手工写，不用 LLM 抽）：

| 节点类型 | 例子 | 量级 |
|---|---|---|
| `place` 地点 / 建筑 | 思源楼、二食堂三楼、图书馆四层 | ~40 |
| `org` 机构 / 院系 | 计算机学院、教务处、一卡通中心 | ~30 |
| `service` 办事 / 服务 | 办校园卡、补办学生证、成绩单打印 | ~40 |
| `item` 物品 / 材料 | 身份证、一寸照、学生证 | ~30 |
| `time` 时段 | 工作日 8:00–11:30 | ~20 |
| `tag` 标签 | 安静、有插座、可通宵 | ~20 |

| 边 | 方向 | 例子 |
|---|---|---|
| `位于` | org→place | 计算机学院 → 思源楼 |
| `属于` | place→place | 二食堂三楼 → 二食堂 |
| `邻近` | place↔place | 思源楼 → 二食堂（**带 `w` 步数，用来算路**） |
| `设有` | place→org | 学生活动中心 → 社团联合会 |
| `负责` | org→service | 保卫处 → 失物招领 |
| `办理于` | service→place | 办校园卡 → 一卡通中心 |
| `需要` | service→item | 办校园卡 → 身份证 |
| `开放` | place→time | 图书馆 → 工作日 7:00–22:30 |
| `具有` | place→tag | 图书馆四层 → 安静 |
| **`别称`** | node→alias | 思源楼 → "主楼" |

> ⚠️ **`别称` 边最容易被漏掉，但不做就哑**。校园里同一个地方有三四个叫法（"主楼""思源楼""行政楼"很可能指同一栋）。§4.3 说"校园词太专有、语义向量会把它模糊掉"——那是**同一个问题的上半句**，下半句就是这张别称表。

### 4.6 检索：入口复用倒排，然后走两跳

**不新写检索器**，四步：

1. **入口**：问题 → 关键词 / 别称匹配 → 命中 1~2 个起始节点（**这一步完全复用 §4.3 那套倒排索引**）
2. **遍历**：从起始节点做**深度 ≤ 2 的 BFS**，只走白名单边类型
3. **组织**：走过的路径**就是答案的骨架**，路径上的节点名填进句式模板
4. **兜底**：跳数超限、或起终点落在图外 → **回落到原来的 top-3 切片 RAG**（原有能力一点不丢）

**为什么是 2 跳不是 3**：校园问句几乎都是「实体—关系—实体—关系—实体」——

「办校园卡」→办理于→「一卡通中心」→开放→「工作日 8:00」。**三跳以上就该去问人了**，这天然接上 §3.2 的 `refuses` 和 `unknown_line`：**答不了不是缺陷，"我不知道"是设定。**

**顺带白捡一个展示点**：`邻近` 边带步数权重 ⇒ 两跳遍历天然吐出一条粗略路线，可以直接喂给地图层的寻路。**"不只是告诉你二食堂在哪，而是带你走过去"**——坐标系是现成的，这一段几乎不额外花成本。（`MapAPI.findPath(from, to)` 本来就有，见 §8——**这条路不用新增任何 API**。）

### 4.7 这条线为什么比"套壳 RAG"值钱

GitHub 上"校园问答"的项目几乎全是 RAG 套壳（检索结果都停在个位数 star）。**多一层图，多的不是精度，是三个别的东西：**

**① 答案可解释。** 向量检索给的是"这几段最像"，图谱给的是**一条路径**——`办校园卡 →办理于→ 一卡通中心 →开放→ 工作日 8:00`。路径能画给玩家看，也能画给老师看。**幻觉在路径上没有藏身之处**：跳不出来就是跳不出来。

**② 图上的事实会走样。** 这是和 §15 的接点，也是别人没有的那一层。GraphRAG 一条线上的工作做的是**检索**，图是只读的；**我们的图会被 NPC 转述**：学长知道「办校园卡→需要→身份证」，他转述给阿姨时丢了这一条边，**阿姨那张图就少一条**。同一张图，**每个智能体持有的是完整度不同的一个副本**。

**③ "图"和"记忆"的差值本身是内容。** 约定：**图谱负责"正确"，记忆负责"磨损"**，两者在 §3.2 的 `knows` 上对接。详见 §16。

> ②③ 是"组合"，不是我们的发明——图谱是公开技术，信息走样是公开现象，
> **把两者接在同一份数据上**是我们要说清楚的事。答辩口径：不宣称首创，只说组合。

### 4.8 成本与影响面

| 项 | 量 | 说明 |
|---|---|---|
| 数据（**主要工作量**） | 200 条三元组 | 五个人分头写，每人 40 条 ≈ **一个下午**。**是数据活儿不是代码活儿** |
| 代码 | **约 80 行** | 入口 0 行（复用倒排）+ 两跳 BFS 约 50 行 + 句式模板约 30 行 |
| 新增依赖 | **0** | 不引向量库、不引图数据库，就是一个 JSON + 一段 BFS |
| 对既有契约的影响 | **0 处需要改** | `knows` 仍是字符串数组，映射到图上时做一次**别称解析**即可 |
| `tools` 字段 | **加一个** | 新增 `walkGraph`，与既有的 `searchKnowledge` 并列 |

**风险**：数据写漏比代码写错更致命——**图上没有的边，NPC 就是真的不知道**，而且这个错误**不会报错、只会安静地少答一句**。

**对策**：三元组写完做一次**连通性自检**（每个 `service` 至少能走到一个 `place`、每个 `place` 至少有一条 `邻近`），当作一条验收项。

## 5. 阿姨 · 丙 —— 众包口碑

> 系统的**活的评价数据**。口碑不是一张静态评分表，而是**有发布者、会随时间变旧**的东西。

### 5.1 她管什么

| 项 | 内容 |
|---|---|
| 场所 | 食堂窗口后（`static`，只在窗口之间挪） |
| 工具 | `getRating()` + `listWindows()` |
| 管什么 | 全校食堂窗口的口碑——**哪个窗口好吃、哪个窗口排队短** |
| 出现时间 | **只在饭点**（见 §13.3） |
| 主动性 | 三人里**最活跃**的一个（见 §13.4） |

### 5.2 口碑数据从哪来：玩家自己写的

口碑没有爬虫、没有编辑，全部来自**玩家的异步痕迹**（§18）：

| 环节 | 发生什么 |
|---|---|
| 1. 打分 | 玩家 A 在跟阿姨说话时顺口说"三窗口的麻辣香锅不错，就是排队久" |
| 2. 落库 | 拆成一条 `reviews.json` 条目，写入**阿姨的公共层** |
| 3. 沉淀 | 随时间衰减加权，与别人的评价合并成窗口得分 |
| 4. 被问到 | 玩家 B 问"哪个窗口好吃"，阿姨读公共层答出来 |

> **没有独立的打分 UI**——这守住了 §2.2 的产品主张：**玩家不需要知道"功能菜单在哪"**。打分是说话的一部分，不是一次表单提交。

### 5.3 口碑怎么变成分数

每条口碑记下六样：哪个窗口、几星、说了什么、有什么标签、什么时候、谁说的。

**评分按时间衰减加权**——旧评价会变淡。食堂换厨师、窗口翻新之后，开学时的好评不该继续压着新评价。

> ⚠️ 别和**记忆检索**的时间因子混：记忆检索走的是 `recency × relevance × importance` 三因子，口碑走这一条独立衰减。**衰减曲线由 3 号定。**

### 5.4 她怎么回答

| 玩家问 | 阿姨怎么答 |
|---|---|
| "哪个窗口好吃" | 报出加权得分最高的窗口 + **自己的转述口吻** |
| "三窗口今天排队吗" | 依据**最近几小时**的条目回答；没数据就说不知道 |
| "二食堂几点关门" | **不归她管**——这是学长那条图谱线的问题 |

**她答不出的两类**：① 没有近期数据（**她不会编**）；② 不是口碑范畴的问题（推给别人）。

### 5.5 展示形态

| 形态 | 说明 |
|---|---|
| 对话 | 主要形态——阿姨用口语转述，带上她的立场 |
| 榜单 | 问"哪个窗口最好"时输出一个排序，卡片式贴在气泡里 |
| 地图图层 | `MapAPI.setLayer('reviews', ids)` 把有口碑数据的窗口在地图上高亮（§8） |

### 5.6 她的人格配置

配置格式与学长（§4.9）完全相同，她的差异点只有三处：

| 字段 | 她填什么 |
|---|---|
| `roam.type` | `static`——窗口后不动，只在窗口之间挪 |
| `tools` | `getRating` + `listWindows` |
| `knows` / `refuses` | 划出边界：管食堂窗口、菜品、排队这些，不管选课、绩点、失物招领 |

> **她的性格怎么写（`persona`）、怎么打招呼、答不上来时怎么推给别人——留给你写**（见附录 C 分工表）。
>
> 她的主动规则表见 **§13.4**。

## 6. 保安 · 老丁 —— 失物招领与报修

> 系统的**到场服务**。他是全图唯一**叫得动**的智能体。

### 6.1 他管什么

| 项 | 内容 |
|---|---|
| 角色 | 保卫处值班 |
| 工具 | `matchLostItem()` + `matchByImage()`【云端】+ `reportRepair()` |
| 管什么 | **失物招领**（文字匹配 + 以图搜物）+ **报修** |
| 移动 | `patrol`——全域多点巡逻（见 §10） |
| 叫得动 | **全图唯一**，08:00–22:00 应答（见 §12） |

### 6.2 机构与载体是分开的

| 层 | 名字 | 含义 |
|---|---|---|
| **机构** | 保卫处 | 职能、知识边界、失物库、报修流程 |
| **载体** | 保安 · 老丁 | 地图上会走动的 sprite |

玩家问的是"保卫处"，但地图上走动的是老丁这个人。**这样命名风格才统一**——学长、阿姨、保安**都是人**。

### 6.3 失物匹配：四维相似度

玩家丢东西时描述往往不准（"蓝色的保温杯，上面有贴纸"），所以不能只靠文字匹配。**四个维度打分后加权求和**：

| 维 | 判据 |
|---|---|
| **类别** | 是不是一类东西（水杯 / 校园卡 / 钥匙 / 耳机…） |
| **地点** | 丢失地与**捡到地**在图谱上离得近不近 |
| **时间** | 丢失时间与入库时间隔了多久 |
| **描述关键词** | 玩家说的话与条目描述重合多少 |

> **四项的具体权重由 4 号定。**
>
> **以图搜物命中时，图像相似度直接替代"描述关键词"这一维**——照片比描述准得多，这正是 §6.4 要解决的那个问题。

**返回**：得分 top-3，每条带**捡到地点**，在地图上标出来（复现现实里"去保卫处认领"的动作）。

### 6.4 以图搜物：唯一一件 CV 要做的事

| CV 任务 | 要训练吗 | 难度 | 耦合模块 | 结论 |
|---|---|---|---|---|
| **失物拍照 → 以图搜图** | 不用（CLIP 零样本） | 低 | 失物招领 | **采用** |
| 失物照片 → OCR 抽文字 | 不用（PaddleOCR） | 低 | 失物招领 | 可选 |
| 建筑照片 → 识别位置导航 | 要自建场景数据集 | 中 | 地图 | 备选 |
| 菜品识别 → 热量价格 | 要标注上千张 | 高 | 口碑 | 不做 |
| 手绘/截图 → 识别地图要素 | 要标注 | 高 | 地图 | 不做 |

**为什么选以图搜物**：

1. **零训练、零标注**，当天就能上线
2. 演示极直观：拍一只水杯 → 秒出 3 条「有人捡到的相似物品」
3. 正好补上失物招领最弱的一环——**丢东西的人描述不清，而照片不用描述**
4. 答辩现场唯一的「真·AI 视觉」展示点

**原理**：CLIP 把图片编码成向量 → 和失物库里预存的向量算余弦相似度 → 排序返回。失物库每条入库时顺手算一次向量，**检索是纯 CPU 计算，不用 GPU**。

**链路**（云端部分详见附录 B）：

```
浏览器（单文件 HTML）          云函数代理（约 30 行）        云端 GPU（按需开机）
  拍照 / 选图         图片 →    注入鉴权 Token        →    CLIP + FastAPI
  base64 编码                  转发到 GPU 实例              以图搜图
  渲染候选结果        ← JSON    超时 800ms 即降级      ←    top-3 结果
```

**注意**：这条路**不破坏单文件零依赖约束**——前端仍是一个 HTML，只多了一个 `fetch`；模型在云端，不在包里。代理层存在的理由：前端不能直连 GPU（跨域 + API Key 泄露 + HTTPS 混合内容）。

### 6.5 报修

玩家在对话里说"三教二楼的水龙头坏了"，走的是和失物同一条通道：

| 步 | 动作 |
|---|---|
| 1 | 玩家说话 → 意图分类命中 `reportRepair` |
| 2 | 抽出**地点**（对图谱做别称解析 → 落到 `place` 节点）+ **问题描述** |
| 3 | 生成工单条目，写入**保卫处公共层**（`visibility: public`） |
| 4 | 其他玩家可以问"我报的修好了吗"——老丁按地点检索公开条目回答 |

工单记下：地点、问题、时间、状态、谁报的。写入公共层，所以**别人也查得到**。

> **不做后台管理端**——那会破坏单文件零依赖约束（§1.5）。工单的"处理"由老丁在对话里更新状态，本身就是一个人格化动作。

### 6.6 他的人格配置

配置格式与学长（§4.9）完全相同，他的差异点：

| `tools` | `matchLostItem` + `matchByImage` + `reportRepair` |

| `knows` / `refuses` | 划出边界：管失物、报修、门禁这些，不管选课、绩点、食堂评分 |

# 第二层 · 地图

## 7. 世界底座：地图本身

一句话：**一张 3/4 俯视的像素校园地图，尺寸与比例由思源楼这一把尺子定死。**

**美术与视角**

- 正交 3/4 俯视（类似星露谷物语），瓦片 32px
- 所有可绘制对象按**落地线排序**——人物走到建筑后面会被自然遮挡，**不需要额外的遮挡遮罩**

**唯一的换算链**（这条链是硬约束，别处不许再定一套）

| 项 | 值 |
|---|---|
| 思源楼真实长度 | ≈ 50 米 |
| PPT 中宽度 | 1.1521 英寸 |
| 游戏内长度 | **450 世界像素** |

由此推出：

| 换算 | 数值 |
|---|---|
| 世界尺寸 | **5208 × 2930 世界像素** |
| 1 米 | ≈ 9.0 世界像素 |
| 1 英寸 | ≈ 390.59 世界像素 |
| PPT 画布 | 13.33333 × 7.5 英寸 |

**可行走区域**：就是碰撞体的补集。巡逻路径点必须落在里面。

**两处已知偏差**（一律按 PPT 画，**不改标尺**）

- 图书馆前的黑三角广场：PPT 里没有，按口述语义自建
- 操场：PPT 只给了 65 × 43 米，放不下标准 400 米跑道——标注差异即可

> 渲染细节（阴影、地面烘焙、精灵装配、各建筑绘制）见《像素校园地图_开发交接文档.md》，本文档不重复。

## 8. 地图能做什么，以及向导 · 小北

**地图对外提供这些能力**（函数名即接口约定，参数见附录 A）：

| 能力 | 用在哪 |
|---|---|
| `focus(placeId)` | 镜头飞向某处并高亮——**AI 带路用这个** |
| `highlight([...])` | 高亮一组地点 |
| `addPin({...})` | 在地图上打标记 |
| `setLayer(name, ids)` | 按条件切图层，如高亮有口碑数据的窗口 |

| `nearestWalkable(x, y)` | 找最近的可行走点 |

**向导 · 小北是这些能力的拟人化出口。**

> 他的配置结构与三个角色完全相同（`agents/guide.json`），差别只在于挂的工具全是地图能力、且不进社交网络。

## 9. 世界时间层：与真实时间对齐

**现在是几点，校园就是几点。**

这是"数字孪生"的**时间维度**，与 §20 的真实坐标映射（**空间维度**）是同一个命题的两半。

**为什么不用游戏内加速时钟**：加速时钟自成一个"游戏时间"，与角色作息（§11）、主动性（§13）、图谱（§4.5）**没有共同的时间基准**，各写各的迟早对不上。对齐真实时间把三者**收敛到同一个时间源**，顺带得到一句能上台面的定位：**真实的人、真实的位置、真实的时刻**。

### 9.1 范围：只对早晚，不做四季

| | 做不做 | 原因 |
|---|---|---|
| **昼夜 / 时段** | ✅ 做 | 全是**叠加层**，不动任何已定稿的精灵 |
| **四季** | ❌ 不做 | 换季要重烘焙三个地面层，而烘焙吃**共享 rng** ⇒ 会重掷全校园地面噪声，整张地图逐点变样 |

> 因此**不引入日出日落算法**（那会把季节带回来），用一张**固定时刻表**。

### 9.2 时刻表直接取真实校园作息——与图谱同源

| 时刻 | 世界变化 | 对应事实 |
|---|---|---|
| 05:00 | 转清晨冷白 | — |
| 06:30 | 二食堂灯亮、开始供餐 | 「二食堂 营业时间 06:30–19:00」 |
| 07:00–17:00 | 白天光照 | — |
| 18:30 | **路灯亮** | 「路灯 开启时间 18:30」 |
| 22:00 | 图书馆闭馆熄灯 | 「图书馆 闭馆时间 22:00」 |
| 23:00 | 宿舍楼熄灯 | 「宿舍 熄灯时间 23:00」 |

这张表和 `campus_kg.json`（§4.5）是**同一份数据**：问答用它回答"二食堂几点关门"，世界用它决定灯几点灭、NPC 几点走。**写一遍，两处用**——这也是角色作息（§11）的数据来源：**NPC 的作息不另编一套，而是读图谱里的营业 / 闭馆时间**。

> ⚠️ 这要求图谱节点带一个 `hours` 字段：「营业时间 06:30–19:00」是**实体 → 值**，不是实体 → 实体，**不要硬塞成一类边**。见附录 A。

### 9.3 三件必须一起定的事

1. **时间覆盖开关是刚需，不是彩蛋**——夜景**没法等到半夜测**。默认态与真实时刻一致，覆盖只在调试与演示时打开
2. **设最暗下限**——深夜也不能黑到看不清。真实 ≠ 可用，一片黑会被当成"页面坏了"
3. **HUD 显示真实时刻**（例：`21:47 · 夜景`）——否则下午答辩时，"对齐真实时间"这个卖点在画面上**完全隐形**，演示应主动把时间拨到晚上给评委看

### 9.4 验收方式与别处不同

**逐时段出图**：清晨 / 白天 / 黄昏 / 夜 / 深夜各截一张，**人眼过一遍**。

> 理由：这类"随时间变化的视觉"，**四套自动验收全绿也判不出对错**。

### 9.5 与 §20 的关系（不合并）

- §20 = **空间**对齐（真实位置出现在像素校园里）
- §9 = **时间**对齐（真实时刻决定校园的样子）

两者合起来是同一句定位，但**不合并**：§20 是可裁剪的附加功能，**时间层是主线**——它服务 §11 的作息与 §4.5 的图谱。§1.4 划的「必交 / 可裁」分界不能混。

# 第三层 · 角色在地图上的行为

## 10. 移动性三档

三个角色各占一档，答辩时天然形成对比：

| agent | `roam.type` | 行为 |
|---|---|---|
| 阿姨 · 丙 | `static` | 食堂窗口后不动，只在窗口之间挪 |
| 学长 · 甲 | `shuttle` | 教学楼 ↔ 图书馆两点往返 |
| 保安 · 老丁 | `patrol` | 全域多点巡逻，**可被呼叫**（§12） |

移动性是一个**配置维度**——差别只在 `roam` 这一段 JSON，引擎是同一份。

**巡逻本身不需要寻路**：走预定义路径点循环即可。路径点必须落在可行走区域内，由 `MapAPI.nearestWalkable()` 校验（§8）。

## 11. 作息：读图谱里的时间

每个角色有一份 `schedule`：

```json
"schedule": [
  { "t": "08:00-12:00", "at": "library" },
  { "t": "12:00-13:00", "at": "canteen_2" }
]
```

**这份作息不另编一套，它读的就是 §9.2 那张时刻表**——也就是图谱里的营业 / 闭馆时间。世界层与知识库就此焊死在同一条时间源上。

**怎么落地**：在算路径点之前先查一次 `schedule`，把 `at` 映射到地图坐标，当作当段的第一个路径点。**约 20 行，纯加法。**

**效果**：NPC 早上在图书馆、中午去二食堂，**玩家能"猜"到他在哪**——从"随机游走"变成"有作息的人"。

## 12. 被呼唤：叫得动的人

保安老丁是全图唯一**叫得动**的智能体。

**效果**：玩家点一下"呼叫"，老丁从他现在的位置**自己走过来**——沿路网绕开建筑，速度比平时快，头顶冒一个「！」，玩家能看见他在赶路。走到玩家面前停下，开口第一句是"来了来了，什么事？"

| 细节 | 效果 |
|---|---|
| 应答时段 | 只在 08:00–22:00 应答，其余时间回一句"忙着呢，一会儿再说" |
| 停下位置 | 停在玩家前方一点，不压在玩家身上 |
| 多人同时呼叫 | 每个人看到的都是"老丁朝我走来"——这是各自的会话状态，互不干扰 |
| 途中 | 那段等待不是延迟，**是仪式感** |

> 另外两个人不响应呼唤——找他们得自己走过去。这是**导航与社交的分工**。

## 13. 主动性：偶遇而非推送

### 13.1 要解决的问题：告警疲劳

低 precision 的主动提醒会导致用户直接关闭该功能。**"何时帮助"比"如何帮助"更难。**

参考工作：ProactiveAgent（四指标 CD / MN / NR / FD）、PASK（DD-MM-PAS 框架）、ProAgentBench。

### 13.2 三层解法

| 层 | 机制 |
|---|---|
| **主动预算** | 每个智能体每天最多主动开口 **1~2 次** |
| **冷却期** | 同一条规则触发后进入 `cooldown`（如 1 天） |
| **重要度分级** | 多条命中时按 `importance` 排序，只发 top-1，其余转信箱 |

**多个智能体抢着提醒**同一个人的问题，靠 `「已告知」` 标记解决——学长告诉过阿姨的事，不会再有第二个人重复提醒你。

### 13.3 校园主动性的特殊之处

主动提醒必须由**「地图 + 时间 + 记忆」三者交叉**才能算出来：

- **地图**：你在哪、你常去哪
- **时间**：现在几点、今天周几（阿姨只在饭点出现）
- **记忆**：你跟我说过什么

**单独的任何一个维度都不足以支撑一次主动提醒。**

### 13.4 主动规则表：三个成员唯一要填的东西

引擎由 2 号写，甲 / 丙 / 丁三个人各交一份规则表。格式：

```json
{
  "agent": "auntie",
  "dailyBudget": 2,
  "rules": [
    {
      "id": "canteen_rest",
      "when":     { "event": "place_closed", "place": "canteen_2" },
      "audience": { "visitedWithinDays": 7, "minVisits": 3 },
      "message":  "…",
      "importance": 5,
      "cooldown": "1d"
    }
  ]
}
```

`when` 是触发条件，`audience` 是"谁该收到"，`importance` 决定和别条冲突时谁先发。**具体写哪些规则、说什么话，由各人自己发挥。**

### 13.5 物理载体：巡逻

主动性终于有了物理载体——**"系统推送"让人烦，"路上碰见跟你说一句"是社交。**

保安走到你附近才开口，告警疲劳天然消失，因为**这不是推送，是偶遇**。

# 第四层 · 多智能体社交

## 14. 社交网络与它的三层约束

**社交网络只有 3 个人、2 条边**：学长 — 阿姨 — 保安，链式结构，**路径唯一**，演示可控。

三个角色**不是预制台词机**——每次说什么，由他们各自真实的记忆决定。但他们也不能没完没了地闲聊，所以有三层约束：

| 层 | 约束带来的效果 |
|---|---|
| **触发层** | 不会没完没了——每对智能体每天最多聊 2 次、间隔至少 2 小时、全局每天最多 6 次 |
| **生成层** | 每次聊什么由"导演"选定，且两位 NPC 各自只看得见自己的记忆，所以信息天然不对称：学长不知道阿姨窗口的排队情况 |
| **准入层** | 不是什么都能外传——只有重要度够高的事才进公共层，**私密信息永不外传** |

**交流发生在后台，不在地图上表演**——没有"两个人站在一起聊天"的动画。

一天被切成 6 个 4 小时时段，每段最多发生一次交流。玩家看不到过程，但**第二天能从另一个 NPC 嘴里听到消息**——感知到的是结果，不是过程。

> **附带收益（对开发很重要）**：社交系统与地图位置系统**彻底解耦**——组长改地图、成员改社交，互不影响，可以完全并行开发。

**初始记忆**：每个智能体预置 5~10 条，保证**没人跟它说话时也聊得起来**，不会冷场。

**调试按钮**：提供"手动触发一次交流"——**开发不用等，答辩可控**。

**成本**：三个智能体每天最多交流 6 次，**约 0.02 元/天**。真社交的代价低到可以忽略。

## 15. 信息走样：社交 = 记忆的复制

**核心洞察**：交流不是播放预制台词——他们知道自己知道什么、知道玩家跟他说过什么，所以同一件事由不同的人说出来，内容天然不一样。

更重要的是：**信息在传播中会衰减。**

| 环节 | 玩家看到的效果 |
|---|---|
| 原始 | A 对学长说："我下周三要交实验报告" |
| 一跳 | 学长转述给阿姨，说的还是原话 |
| 二跳 | 阿姨转述时已经变成"**听说**有人要交报告"——话变短了，来源变模糊了 |
| 三跳 | 再往外传只剩一个模糊印象：具体时间、是谁，都不确定了 |

> **走样不是我们发现的，是已经被反复验证过的现象**——近两年有多篇专门研究"LLM 传话游戏"的工作（附录 G），证明信息在迭代传递中会失真、会漂移向某个"吸引子"。它们证明的是**会发生**；本项目做的是让它在**一个 50 名真实玩家的校园里、以每天一条消息的节奏、被围观地发生**。
>
> 预制模板做不到"走样"，因为走样要求**每一跳都是当场生成的**。答辩时只要让同一条信息走三跳，效果自己会说话。

---

## 16. 图谱的磨损：同一张图，不同的完整度

除了记忆会走样，**图本身也会缺**。

每个智能体持有的是**完整度不同的一个副本**：学长知道「办校园卡→需要→身份证」，他转述给阿姨时丢了这一条边，**阿姨那张图就少一条**。

约定：**图谱负责"正确"，记忆负责"磨损"**，两者在 `knows`（§3.2）上对接。

| 情况 | NPC 的表现 | 玩家感知 |
|---|---|---|
| 图上有、他也记得 | 完整答出，还能带上路径 | 靠谱 |
| 图上有、他没记住（不在他的 `knows` 里） | `unknown_line`：「这个我真不知道，你去问问保卫处吧」 | **他不是不肯说，是真的不知道** |
| 图已更新、他记得旧的 | 好心告诉你**过时的**信息 | **最有说服力的一刻**：真人也会这样 |

> §15 演的是"信息被压缩"，§16 演的是"信息本来就缺一块"——**两者是不同的机制，玩家能分辨出来**。演示见附录 D。

# 第五层 · 两种模式

## 17. 单机模式：50 个独立会话

**核心判断：不做玩家实时互见。**

- 每个用户是一个**独立的单机会话**——独立的位置、独立的对话、独立的私密记忆
- 50 个人**共享**三样东西：**世界状态** + **智能体记忆的公共层** + **异步痕迹**
- **没有实时同步，没有并发位置广播，没有 WebSocket**

> **社交模式（§20，附加功能）是这条判断的唯一例外**：开启后，所有开着这个模式的人互相可见。主线的三样共享数据一个字不改，默认关闭。

> 打个比方：**50 个人各自打开同一个单机游戏，但共用一个 NPC 的记忆。**

| | 数量 | 内容 |
|---|---|---|
| **共享层** | **2 份** | 世界状态（二食堂今天休息）+ 公共记忆层（智能体社交写入、50 人的足迹与点评） |
| **会话层** | **50 份** | 各自的位置、私密记忆、对话历史、信箱 |

**这就是不需要 WebSocket 的原因。**

---

## 18. 异步痕迹：用户之间怎么"见面"

用户之间不说话，但通过 NPC 交换信息：

| 痕迹 | 写入 | 体现 |
|---|---|---|
| 足迹 | A 去过哪 → 公共层 | B 打开地图看到"3 人最近来过" |
| 点评 | A 给二食堂打分 → 阿姨的公共层 | 所有人都能问到（§5.2） |
| 失物 | A 丢了卡 → 保卫处公共层 | 捡到的人一问就知道 |
| 遗留物 | A 在校园某处埋下一个 → 公共层 | B 闲逛到那儿时发现（§22.6） |
| 「已告知」 | 学长告诉过阿姨 → 标记 | 不会重复提醒同一个人 |

---

## 19. 双通道与信箱

**核心洞察：大部分主动提醒根本不是私密信息。**

| 通道 | 触发源 | 受众判定 | 成本 |
|---|---|---|---|
| **① 公共广播**（一对多） | 世界事件 | 由事件本身决定 | **1 条，与用户数无关** |
| **② 定向提醒**（一对一） | 该用户的私密记忆 + 状态 | 个体条件命中 | O(活跃用户)，严格限频 |

**受众判定表**

| 世界事件 | 谁该收到 | 怎么判定 |
|---|---|---|
| 二食堂今天休息 | 常去二食堂的人 | 位置历史：7 天内到访 ≥ 3 次 |
| 傍晚暴雨 | 所有人（在线才推） | 无条件 |
| 四级报名后天截止 | 记忆里标记过要考四级的人 | 公共记忆检索 |
| 南门施工封路 | 常走南门的人 | 位置历史 |

**定向提醒限频**：每人每天 **≤ 1 条**，每个智能体每天 **≤ 2 条**；冲突时按 `importance` 排序，只发 top-1，其余进信箱。

**成本模型**

| 项目 | 调用量 | 与用户数的关系 |
|---|---|---|
| NPC 日常走动 + 3 智能体社交 | **0** | 无关 |
| 公共广播 | 3~5 次/天（模板生成，多数不调 LLM） | **常数** |
| 定向提醒 | 上限 50/天，实际命中约 10 | 线性但极小 |
| 玩家主动搭话 | 每人在线 3~5 轮 | 用户自己触发 |

> **「谁需要知道」由世界事件决定，不由用户数决定。** 50 个用户规模下，主动性成本与 5 个用户处于同一量级。

**信箱机制**

| 状态 | 呈现方式 |
|---|---|
| 在线 | NPC 在地图上冒气泡（复用现有渲染，零新代码） |
| 不在线 | 写入 `inbox[playerId]`，上限 5 条，按重要度排序、同类合并 |
| 下次登录 | 一次性呈现：「你不在的时候，阿姨跟你说……」 |

> 好处：不打扰 + 不丢消息 + 天然解决跨天问题。

---

## 20. 社交模式：真实坐标映射（附加功能，可裁剪）

**整个附加功能唯一要说明的事**：玩家站在真实的思源楼前，地图上的自己就在像素思源楼前；从南门走到图书馆，地图上的自己也同步走一遍。

| 项 | 说明 |
|---|---|
| 性质 | 附加功能，**不做也能交** |
| 依赖方向 | **单向**：§20 依赖主线，主线不依赖 §20 |
| 额外代价 | 唯一要求 HTTPS 与后端进程（位置服务，约 30 行）的部分 |
| 收益 | 项目最强的记忆点，也是答辩第一屏 |

**它打破了哪三条旧约束**（都只在开启社交模式时才被打破）

| 旧约束 | 出处 | 附加功能下的状态 |
|---|---|---|
| 不做玩家实时互见 | §17 | 仅社交模式开启时打破，默认仍关闭 |
| 不引入后端 | §1.5 | 多一个位置服务进程（约 30 行），不进主链路 |
| `file://` 双击即可用 | 附录 E | 社交模式必须 HTTPS / localhost，其余功能不受影响 |

**三点已确定的结论**

| 结论 | 说明 |
|---|---|
| **缩放不用猜** | 每米 9 个世界像素，已由思源楼标尺（§7）唯一确定 |
| **两个校门就够** | 两处校门的真实坐标 + 地图坐标，即可把真实校园精确叠到像素校园上；第三个校门用来验证准不准 |
| **北要朝上** | 真实正北要转到像素地图的上方 |

**三个会遇到的现象（都已有对策）**

| 现象 | 不加处理的后果 | 处理后的效果 |
|---|---|---|
| GPS 有误差 | 自己漂进墙里、漂到湖里 | **自动吸附回路边** |
| `file://` 打开时定位不可用 | 定位请求毫无反应 | 提供**手动在地图上点选位置** |
| 室内没有信号 | 教学楼里位置乱跳 | 降级为"你在这栋楼的门口" |

**所有在线玩家在同一张地图上**

| 效果 | 说明 |
|---|---|
| 刷新 | 位置每秒更新一次，看起来是连续走动的 |
| 下线 | 关掉页面立刻从别人地图上消失，无需任何操作 |
| 规模 | 50 人同时在线，开销可以忽略 |
| 互不干扰 | 没开社交模式的人依旧在"单机" |

**隐私默认值（不可商量）**：默认关闭，必须主动开启 / 只显示昵称，不显示学号与精确坐标 / 关闭页面即刻下线，无历史轨迹 / 提供**隐身**开关。

**社交模式不能只是"看到别人"**，否则就成了"地图上多几个会动的点"。三个动作：

| 动作 | 效果 |
|---|---|
| **打招呼** | 点一下附近的玩家 → 对方收到提示，走信箱通道（§19） |
| **附近的人高亮** | 屏幕上的人被高亮标出，一眼看得清谁在附近 |
| **位置邀请** | "我在图书馆，过来吗"，附一个地点标记 |

**甜蜜副作用**：两个原本要额外做的功能**免费获得**——「足迹」变成真的（`on('enter')` 记的是真实到场）；**答辩第一屏**（打开地图，看到自己的真实位置在像素校园里跳动）。

> **对主线的影响：世界状态、公共记忆层、异步痕迹——前三样一个字不改。** 这就是把它做成"附加功能"的价值：**是新增一件东西，不是改原来三件。**

## 21. 单机 / 社交：一张对照表

| | **单机模式**（默认，主线） | **社交模式**（§20，可裁剪） |
|---|---|---|
| 能看到真人吗 | ❌ 地图上只有自己 | ✅ 所有开着该模式的人互相可见 |
| 位置从哪来 | 玩家自己走（虚拟位置） | **真实 GPS**，吸附到路边 |
| 交互范围 | 只能跟 NPC 说话 | 还能跟真人打招呼、发位置邀请 |
| 用户之间怎么联系 | 留下能被发现的痕迹——**异步、匿名**（§18、§22.6） | 直接看到、直接打招呼 |
| 共享的数据 | 世界状态 + 公共记忆 + 异步痕迹（3 样） | 前三样不变，**另加**实时位置 |
| 需要后端吗 | ❌ 零后端 | ✅ 一个位置服务进程（约 30 行） |
| 打开方式 | `file://` 双击即可 | 必须 HTTPS / localhost |
| 默认状态 | **开启** | **关闭**，必须玩家主动开启 |
| 定位不可用时 | 不受影响 | 降级为手动点选 |
| 可裁剪性 | 必须交 | 不做也能交 |

> **两条判断**：
> ① 单机模式的"50 个真人"是**异步共存**——你看不见别人，但别人的足迹、点评、丢的东西都在。
> ② 社交模式不是"把单机变成网游"，它是**新增一层**，关掉之后主线一个字不变。

# 第六层 · 玩法

## 22. 玩法：怎么让人来，怎么让人再来

### 22.1 先分清两件事

**揽客**是让没打开过的人第一次打开；**留人**是让打开过的人明天再来。

前面二十一节解决的都是"来了能干什么"，这一节解决"**为什么要来**"。

一条判据，用来筛掉俗玩法：

> **把"校园"两个字换成别的，这个玩法还成立吗？**

- "下雨就换个贴图"——换哪个游戏都成立 → 俗
- "满地图捡东西"——换哪个游戏都成立 → 俗

所以下面六个玩法**只从几样别人没有的东西里长**：

| 从哪长出来 | 玩法 |
|---|---|
| **真实时间**（§9） | 「今天」 |
| **真实坐标**（§20） | 「此刻」 |
| **多智能体记忆**（§3、§15） | 「传说」、「校园猫谱」 |
| **一张考据级精细的地图**（§7） | 「到此一游」 |
| **50 人共享的公共层**（§17） | 「遗留物」 |

> 六个玩法都不新开引擎，**全是已有机制的重新组合**。

### 22.2 「此刻」——你在哪，地图上就在哪

社交模式下（§20），你在校园里的真实位置，就是地图上那个像素小人站的位置。

于是不需要任何任务系统，就有了一个玩法：**看看我现在的样子**。

- 我站在思源楼前，地图上我也站在思源楼前
- 我走到明湖边，地图上鸭子在离我几米的地方游
- 天是真实的——傍晚打开，地图上也是傍晚

它不是任务，是**镜子**。

**主要作用：揽客。** 截图就是"我在学校，这是我的像素分身"——这是全项目最容易往外传的一张图。

### 22.3 「传说」——散在三个 NPC 脑子里的校园野史

**这是六个里最值的一个，也是唯一一个别人抄不走的。**

校园里本来就有传说，比如：明湖的鱼是谁放的、老体育馆为什么是 13 级台阶、南门那块石头上六个金字是谁写的。（**具体写哪几条留给你们定**，这里只定机制。）

这些**不进图谱**——它们不是"正确信息"，是野史。它们只存在于 NPC 的记忆里，而且：

| 特性 | 说明 |
|---|---|
| 三个人记的不一样 | 学长听说的一个版本、阿姨记得另一个版本、保安是当事人 |
| 要追问才挖得出来 | 不是问一句就给，得多问几轮 |
| 拼起来才完整 | 单问一个人只能听到半截 |

于是 §15 那个"信息走样"**从缺陷变成了内容**：正常问答里走样叫"答不准"，在这里**走样本身就是答案**。

**玩家怎么玩：传说任务栏**

- 图鉴里单开一栏「传说」，列着**问号条目**——只给题目（"明湖的鱼是谁放的？"），不给答案
- 玩家自己去找：问 NPC、翻地图
- 拿到说法后**自己输入**；**语义相同**即算解开，条目点亮
- 三个人各点亮一次，**拼合**出完整版

> **预设答案 = 三个碎片拼合后的完整版**，不是另写一个标准答案——否则就否定了"三个人记的不一样"这个机制本身。
>
> **判据不是"文字一致"而是"要素命中"**：野史本来就没有标准措辞，玩家说"是 98 级毕业生放的"和"九八年那届放的"都该算对。每条传说预设 **3~5 个关键要素**，命中即通过——**可零 LLM 兜底**（关键词 + 同义词表），有 LLM 时再判得更宽（走 §23 降级链）。
>
> **成就 = 本地点亮，不进排行榜**。§22.8 否掉积分榜是因为要后端，本地收集不需要——载体就是 §22.5 那张图鉴，**不另做一套菜单 UI**。
>
> 玩家之间会互相传答案——**不用防**，口口相传本来就是「传说」的传播方式。

**主要作用：揽客 + 留人。** 玩家会跟同学说"你去问保安明湖的鱼试试"——这是口口相传。

**答辩价值**：别的组展示"我们的 AI 答得准"，你展示"**同一个问题问三个人，三个不同的答案，而且都对**"。技术亮点直接变成演示内容。

> 依赖 §3 记忆与认知边界、§15 信息走样。**不需要新引擎**——每条传说就是一条不写进图谱的记忆条目，挂进三个人各自的 `knows`。
>
> **顺带救活"寻物"**：保安手上那批无人认领的失物（§6.3），每一件都是一条校园记忆的碎片——什么东西、什么时候、在哪儿捡的。不是"撒东西让人捡"，是**挖校园记忆**。

### 22.4 「今天」——真实世界的一次性事件

"天气彩蛋"本身太薄了，加一层就厚了：**事件是真的，而且只发生一次**。

- 今天下雨 → 地图上也在下雨
- 今天中秋 → 明湖上有一轮月亮
- 今天下雪 / 今天日落特别好看 / 今晚有流星

关键在于**不可预期、过期不候**——用户会想"今天有什么不一样"。

**主要作用：留人。** 这是 FOMO。

> 数据来源：真实日期（本地就有）+ 真实天气（可选，接天气 API，走 §23 降级链）。
>
> **成本：中。** 日期驱动的几条先做，成本低；天气驱动的要求联网，**列为可裁**。

### 22.5 「到此一游」——让已经画好的东西被看见

地图里已经画好的东西，现在**没有任何机制让玩家注意到**：南门校名石上那六个金字是照着实拍逐点还原的、思源楼顶的灯笼和天线针照片里真有、雕塑其实是齿轮和铁砧不是校徽……

**走到跟前才看得到**：走到地标 → 弹一张小卡片（名字 + 一句话来历）→ 收进图鉴。

一张卡片讲一个考据细节，**走完一圈等于把这张地图的制作过程看了一遍**。

**主要作用：留人 + 揽客。** 而且它**一鱼两吃**——卡片文案本身就是"我们地图做得多细"的答辩证据。

> 依赖 §8 地图能力。**新美术为零**——卡片讲的就是已经画好的那些东西。
> 图鉴同时是 §22.3 传说、§22.6 遗留物和 §22.7 校园猫谱的收集容器——**四个玩法共用一张图鉴**，不多做 UI。

### 22.6 「遗留物」——单机模式里的漂流瓶

**玩法一句话**：你在校园某个角落埋下一个东西；**别人的单机模式里也会出现**；他闲逛到那儿，发现了。

**架构上零成本，且不破任何约束**：单机模式本来就共享三样东西——世界状态、公共记忆的公共层、异步痕迹（§17）。遗留物就是**往公共层加一条记录**，和"足迹与点评"同构。

- 不需要后端、不需要 WebSocket、不需要实时
- 准确说不是"实时同步"，是**每次打开时，世界已经是新的**（§17 明确"没有实时同步"）
- **你不需要在线，你的东西也在世界里**

**三种形态**（由简到繁，可只做第一条）：

| 形态 | 是什么 |
|---|---|
| **小图标** | 走过去看到地上有个东西，纯装饰 |
| **道具** | 可以捡走，收进 §22.5 的图鉴 |
| **一张字条** | 带一句话——**内容才是彩蛋的灵魂** |

**为什么留人：闲逛第一次有了回报。** 现在的单机模式，闲逛没有意义——没有理由去明湖边上绕一圈。有了遗留物，**每个角落都可能有人放过东西**。

**为什么揽客**：截图就是"我在明湖边捡到一个东西，**不知道是谁留的**"。

**三条约束（不设就会烂）**：

| 约束 | 为什么 |
|---|---|
| **限流**——每人每天只能埋几个 | 否则地图上全是垃圾 |
| **会过期**——埋下去几天没人捡就消失 | 过期才有"我发现了"的运气感（和 §22.4 同一种心理） |
| **匿名**——单机模式下不知道是谁埋的 | 见下 |

> **匿名是最重要的一条。** 显示"张三埋的"就变成社交动态；不显示，才是**漂流瓶**。
> 而且这是**双向的不确定**——埋的人也不知道会不会被捡到。

**「位置是信息的门禁」在这里才成立**：一句话不是发在广场上，是钉在明湖边上，**谁走到谁看见**。

**和「传说」互补**：传说讲的是**学校的过去**（NPC 记得），遗留物是**同时代的人**（真人留的）。一个纵向，一个横向。

**社交模式多出来的是什么**：不是"能不能看到别人留的东西"（单机也能），而是**知道它此刻属于谁**。

> 依赖 §18 异步痕迹、§8 地图能力。**新引擎为 0**——公共层多一个字段而已。
>
> **不要和 §6.3 的失物混在一起**：失物是"丢了要找回"（保安的活儿），遗留物是"留了等你发现"（玩家的）。两套数据、两套语义。

### 22.7 「校园猫谱」——每只猫都单独记得你

校园里本来就有猫：食堂后门、图书馆台阶、思源楼草坪、明湖南岸影壁、老体育馆那 13 级台阶上……每只都有自己的**领地**和**脾气**（有的亲人、有的怕生）。

**核心：好感度不是进度条，是一套行为。**

| 档 | 它怎么对你 |
|---|---|
| 陌生 | 远远看见你就跑 |
| 眼熟 | 不跑，但你走近它退 |
| 熟 | 让你靠近，**但不让摸** |
| 亲近 | **让你摸**，在你脚边蹭 |
| 很亲 | **主动走向你**，跟你走一段路 |
| 最亲 | 在你常出现的地方**等你**（罕见） |

**不喂就往下掉档。** 掉档是**渐进**的，不是断崖——玩家不是突然发现"猫没了"，而是察觉到"**它最近不太理我了**"。这种"察觉到变化"本身就是情感。

> 掉到「熟」就是**它不再主动靠近你**；掉到「眼熟」就是**你想摸它会走开**。
>
> **猫不会饿死，只会疏远**——有代价所以有牵挂，不残酷所以没负担，而且是**可以重新建立**的。这是它和电子宠物的分水岭。

**多只，各自独立**：这只跟你熟，不代表那只跟你熟——一只一只来。认识一只，图鉴点亮一格。

**它会过日子**（读 §9 时间层）：早上在食堂后门等早饭、中午在台阶上睡、下午在草坪、晚上不见了。

**主要作用：留人 + 揽客。** 演示性极强——同学打开游戏，那几只猫见他就跑；你走过去，能摸。

> 依赖 §3 记忆、§9 时间层、§10 移动性（领地就是 `roam` 的另一种配置）。**零新引擎**——好感度就是记忆系统里的一条记录。
>
> **衰减以「周」为单位，不是「天」**——以天为单位就变成每日任务了（§22.9）。
> **不给玩家看好感度数字**，行为就是呈现。
> **"喂"具体怎么触发（要不要食物、食物从哪来）留给你们定**；但**不做猫粮货币和物品栏**——那会把系统复杂化，也破坏"不点菜单"。
> **这是唯一一个要新美术的玩法**（3~5 只猫的毛色花纹差异），精灵复用地图的人物绘制系统。

### 22.8 成本与取舍

| 玩法 | 新美术 | 新引擎 | 依赖 | 档 |
|---|---|---|---|---|
| **传说** | 0 | 0 | 记忆系统 + 图鉴已有 | **必做** |
| **遗留物** | 0 | 0 | 共享层已有（§17） | **必做** |
| **到此一游** | 0 | 0 | 地图资产已有 | 低 |
| **此刻** | 0 | 0 | 社交模式 + 时间层已有 | 低 |
| **今天**（日期部分） | 少 | 0 | 时间层 | 低 |
| **校园猫谱** | **有**（3~5 只猫） | 0 | 记忆 + 时间层已有 | 低 |
| **今天**（天气部分） | 中 | 0 | 天气 API | **可裁** |

**只做一样，做「传说」**——零成本、复用已有技术、且唯一一个抄不走。
**做两样，加「遗留物」**——同样零成本，且**单机和社交两种模式下都玩得起来**。
**做三样，加「到此一游」**——让已经画好的地图资产变现。
**要新美术的只有「校园猫谱」一个**——它不便宜，但**情感强度最高**，是唯一一个"你会主动回来看它"的玩法。

### 22.9 不做

- **排行榜 / 积分 / 抽卡 / 体力**——要后端，且与 §17 的 50 个独立会话架构打架
- **系统无限撒的收集品 / 每日签到 / 日常任务**——能被搬到任何游戏里，就是俗
  （**「遗留物」不在此列**：它是玩家埋的，有限、会过期、带内容，不是刷不完的收集点）
- **给遗留物加点赞 / 评论 / 关注**——一旦能互动就变成社交动态，**漂流瓶的味道就没了**（§22.6）
- **猫会饿死 / 会消失**——疏远就够了；**会死的东西没人敢养**（§22.7）
- **把猫的好感度做成进度条**——行为就是呈现，一个数字会把"它认识我"贬值成"我刷到了 73"（§22.7）
- **任何依赖"实时校园数据"的玩法**（教室占用、监控之类）——不能合法获得，不碰

# 收尾

## 23. 断网与降级链

**原则：把 LLM 花在玩家看得见的地方。**

| 用途 | 不花的后果 | 花了的体验 |
|---|---|---|
| 玩家开口说话 | 自由文本没法穷举，只能答非所问 | **听得懂人话** |
| NPC 之间交流 | 只能播预制台词，信息不会走样 | **真社交**（本项目创新点） |
| 记忆压缩 | 只记得住当天的对话 | 记得到上周你随口说过的事 |
| 主动提醒的措辞 | 像系统通知 | 像路上碰见跟你说一句 |

**成本**：50 人全量放开约 **0.5~0.8 元/天**，一个月 30 元以内。**这不是约束。**

**降级链仍然要做，但目的从"省钱"变成"保命"**：

| 级 | 手段 | 效果 |
|---|---|---|
| ① | 意图分类（纯关键词） | 常见问题根本不进 LLM |
| ② | 查缓存（**按意图而非问题原文**） | 同一类问题只生成一次，命中率 70%+ |
| ③ | 调 LLM | 剩下的长尾交给它 |
| ④ | **零 LLM 兜底** | **断网 / 没额度时，NPC 依然答得上话，地图依然跑得动** |

> 按意图缓存的命中率可达 70%+，按原文只有 20%——同一处设计，既省钱又提速。
> **零 LLM 兜底是答辩断网的保险，也是开发期的免费调试通路。**

## 24. 一页总结

**底层**是一个世界，
**中间**是一个引擎，
**上层**是三个人，
**外面**是 50 个互不相识的自己。

- 社交 = 记忆的复制，而复制会走样——**走样是公开研究证过的现象，我们让它在一个有 50 个真人的校园里被围观地发生**
- 主动 = 预算 + 冷却 + 重要度，**成本与用户数无关**
- 功能 = 智能体 = **工具集 + 人格配置**
- 巡逻 = 用时间换空间，**把覆盖面从个位数拉到几十人**
- 呼唤 = 叫得动的人**自己走过来**——不只是回答，是到场
- 附加（§20）= 真实坐标映射，**真实世界的自己出现在像素校园里**
- 玩法（§22）= 只从真实时间、真实坐标、多智能体记忆里长——**换个校园就不成立，才算数**
- 「传说」（§22.3）= 野史不进图谱，**问三个人三个答案**；玩家自己拼出完整版点亮成就——**走样从缺陷变成内容**
- 「遗留物」（§22.6）= 玩家埋、别人捡，**单机模式就能互通**——不破 §17 的三样共享，一个新字段
- 「校园猫谱」（§22.7）= 每只猫**单独记得你**；不喂只会**疏远**、不会死——**唯一一个新美术**，情感最强

| `campus_kg.json` | 五人分摊 | `nodes[]` / `edges[]` / `templates{}` | §4.5 |

**图谱的四条硬约定**

1. **`ref` 指回 `campus.json` 的 `places[].id`，图谱里不许再存一份坐标**（沿用本项目纪律：派生量只存一份）
2. **`src` 必填**，取值 `人工` / `LLM抽取` / `NPC转述`——用于追溯，也是"信息谱系视图"的数据基础
3. **`templates` 与边类型一一对应**：新增一种边必须同时补一条模板，否则那条边答出来是一串 id
4. **`alias` 挂在节点上**，不单独建节点——别称是入口问题，不是图的形状问题

> **`hours` 字段**（§9.2 的要求）：节点需要携带营业 / 闭馆时间（如「二食堂 06:30–19:00」）。它是**实体 → 值**，建议做成节点上的属性位，**不要硬塞成一类边**。

## 附录 B · 技术选型与工程口径

| 模块 | 爬虫 | RAG / 向量库 | 视觉检测 | 实际做法 |
|---|---|---|---|---|
| 地图底座 | 不用 | 不用 | 不用 | Canvas 2D 手绘 + 数据表烘焙 |
| 校园信息库 | **不用** | 不用 | 不用 | 人工整理 → 三元组 **200 条** + 文本切片 **800 条** |
| AI 问答引擎 | 不用 | **轻量版** | 不用 | 关键词命中图谱入口 → **两跳遍历**；答不了再回落 top-3 片段 |
| 众包口碑 | 不用 | 不用 | 不用 | 数据结构 + 时间衰减加权 |
| 失物招领 | 不用 | 不用 | **用（云端）** | 四维相似度打分 + CLIP 以图搜物 |

**统一技术栈口径（答辩用）**

```
渲染层   Canvas 2D（地图 + NPC + 气泡）          组长
引擎层   原生 JS，无框架无构建                    一份
数据层   5 个数据 JSON + 4 份人格配置
         （campus / knowledge / campus_kg / lostitems / reviews）
智能层   纯规则优先，LLM 兜底（可选，断了也能跑）
存储层   localStorage 分片：world / publicMemory / player_<id>
```

> 四个智能体的技术栈**没有任何差别，差别只在数据**。

**云端 CV 的运维要点**：冷启动约 2 分半（开机 90 秒 + 模型加载 30 秒），热机后单张推理约 100 毫秒——**慢的是开机，不是算力**。四条防翻车：答辩前 10 分钟预热 / 代理设 800ms 超时降级 / 云平台设无操作自动关机 / 提前录 30 秒演示视频兜底。

**成本**：GPU 实例开发调试约 20 小时 + 答辩演示约 3 小时，**合计约 60 元**。

## 附录 D · 演示脚本

**主脚本：一条信息走三跳**

1. 开**两个浏览器窗口**（A / B），各自独立会话
2. A 跟学长说"我下周三要交实验报告" → 写入 A 的**私密**记忆
3. 点"手动触发一次交流"，学长把这件事说给阿姨
4. 再触发一次，阿姨说给保安——**每多传一次，话就短一截、来源就模糊一分**
5. B 分别去问阿姨和保安：从阿姨嘴里听到的是"**听说**有人要交报告"，从保安嘴里只剩一个模糊印象
6. **关键帧**：两个窗口里，学长站在**同一个位置**

> 一句话：**世界只有一个，会话有 50 个**；而信息在传话中会走样。

**副脚本 1 · 叫保安（失物招领）**
点"呼叫" → 老丁自己走过来 → "我饭卡丢了" → 命中候选 → 地图标出捡到地点。
> 那段等待不是缺陷，是仪式感；**"叫得动"本身就是交互设计**。

**副脚本 2 · 视觉以图搜物**
描述不清 → 拍照 → 云端 CV 返回 top-3；**若网络不通，主动演示降级到文字匹配，反而加分**。

**副脚本 3 · 主动性**
演示一次公共广播（二食堂休息 → 只有常去的人收到）和一次定向提醒（四级报名截止 → 只有标记过的人收到），**证明不是群发**。

**副脚本 4 · 同一张图，不同的完整度**（接在主脚本之后演，两段共用同一个"信息走样"的话头）

1. 玩家问学长：「**办校园卡要去哪、几点去？**」
2. 学长完整答出：**一卡通中心，在思源楼，工作日 8:00–11:30**（图上三跳，他全有）
3. 同一个问题**原话**去问阿姨 → 她只答出地点，**答不出开放时间**
4. 玩家追问 → 不是她不肯，是**她那张图少一条边**

> 主脚本演的是"信息被压缩"（§15），副脚本 4 演的是"信息本来就缺一块"（§16）——**两者是不同的机制，玩家能分辨出来**。

## 附录 E · 风险与协作纪律

**风险清单**

| 风险 | 影响 | 对策 |
|---|---|---|
| 云端 GPU 冷启动 | 答辩现场等待 2 分半 | 提前 10 分钟预热；录屏兜底 |
| 现场网络不通 | CV 不可用 | 800ms 超时降级；主动演示降级流程 |
| 忘记关机 | 一夜烧几十元 | 设无操作自动关机 |
| 扩图工作量超预期 | 阻塞其他模块 | 优先保证思源楼 + 主干道 + 5 校门 |
| 智能体配置不齐 | 少一个 NPC | 架构容错：缺人只少 NPC，地图和引擎照跑 |
| 主动性过度打扰 | 用户关闭功能 | 预算 + 冷却 + 重要度三级约束 |
| **图谱数据写漏** | NPC 安静地少答一句，**不报错** | 三元组写完做**连通性自检** |
| 操场尺寸与 PPT 不符 | 被质疑 | 按 PPT 绘制，文档标注差异，**不改标尺** |

**协作纪律**

1. **接口契约先行**：六份契约（附录 A）先冻结，再各自开工
2. **Mock 数据**：没有真实数据时用 mock，不要等
3. **Git 分支**：每人一个 feature 分支，主干只接受可运行版本
4. **单文件原则**：任何人的产出最终必须能合并进 `campus.html`，不得引入外部依赖

**已知踩坑（血泪）**

| # | 坑 | 解决 |
|---|---|---|
| 1 | 写文件到 `%TEMP%` 被拒 | 先写项目工作目录，再 `Copy-Item` |
| 2 | PowerShell `.ps1` 中文注释吞换行 | 脚本用**纯 ASCII** |
| 3 | 函数名撞 PowerShell 别名（`CAt` vs `cat`） | 改名 |
| 4 | `Get-Content -Raw \| ConvertFrom-Json` 读 UTF-8 乱码 | 改用 `[System.IO.File]::ReadAllText` |
| 5 | 终端输出被截断 | 写文件再读；用无 BOM UTF-8 |
| 6 | 浏览器 `evaluate` 报 `"undefined" is not valid JSON` | 用括号包裹的箭头函数 + 逗号表达式 |
| 7 | 截图工具不可用 | 改用 `getImageData` 做字符画采样核验 |

> 地图渲染的坑（虚时钟、共享 rng、精灵遮挡等）见《像素校园地图_开发交接文档.md》。

## 附录 F · 可借鉴机制与对标

**对标表（答辩材料，一行代码都不用改）**——**我们的每一项都是组合出来的，不是单点模仿。**

| 维度 | Stanford Smallville | a16z AI Town | AgentSociety | **本作品** |
|---|---|---|---|---|
| 记忆流 / 私密层 | 有 | 简化版 | 有 | 有：public/private + `visibility` + `playerId`，**50 个真人各自私养一份** |
| 反思（Reflection） | 有 | 无 | 有 | 无 → 中成本项 |
| 计划 / 日程 | 有 | 无 | 有 | **有**（`schedule` 读图谱时间，§11） |
| 关系追踪 | 有 | 无 | 有 | 无 → 中成本项 |
| **信息衰减 / 走样** | 无 | 无 | 无 | **有（创新点一）** |
| **50 个真人共养同一份公共记忆** | 无 | 无 | 无 | **有（核心）** |
| **主动性有物理载体** | 无 | 无 | 无 | **有（保安巡逻 → 偶遇而非推送）** |
| 单文件、零依赖、零构建 | 无 | 无 | 无 | **有** |
| 规模 | 25 个智能体 | 多人小镇 | 十万级智能体 | **3 个 NPC × 50 个真人玩家** |

> **怎么用这张表**：老师问"你们和斯坦福那个小镇有什么区别"，答案不是"我们做得没他好"，而是——
> 「**他把 25 个 AI 放在一个假镇上；我们把 3 个 AI 放在一个有 50 个真人的真校园里，而且信息会在他们之间走样。**」
> 上表第 5、6、7 行是三行空白——**这是我们的位置**。

**性价比最高的四条（先做这四条）**

| # | 机制 | 我们现在的状态 | 借什么 | 成本 | 展示效果 |
|---|---|---|---|---|---|
| ① | **`schedule` 日程驱动行为** | §11 已落地 | 算路径点前先查 `schedule` | ≈20 行 | NPC 有作息，**玩家能"猜"到他在哪** |
| ② | **记忆检索三因子** | 只用 `importance` 一档排序 | 加 `recency` × `relevance`（做了图谱后升级为"图上相关"） | ≈15 行 | 记忆从"一张列表"变成"一次回想" |
| ③ | **空闲自语** | 没对话时 NPC 完全静止 | 无对话时每 30~60 秒从自己记忆里冒一句自语气泡，**模板填充不调 LLM** | ≈10 行，**0 元** | **最便宜的"活着"信号** |
| ④ | **可解释的主动性** | §13.1 引了 CD / MN / NR / FD 四指标，**但一个都没实现** | 每次主动开口记一条四元组，调试面板显示 | ≈15 行 | 「我们的主动性是**按这四个指标量的**」 |

> ④ 最"名不副实"：**引了就得能用**。被追问"那你们的 CD 是多少"答不上来，反而减分——要么实现（只要 15 行），要么把引用删掉。

**中成本、但展示效果最强（看工期决定）**

| 机制 | 借什么 | 备注 |
|---|---|---|
| **反思（Reflection）** | 定期把最近若干条记忆喂给 LLM 归纳成一条高阶记忆 | 低风险。问保安"最近学校有什么事"，他能给出**归纳** |
| **玩家投毒** | 玩家说的假话同样进入传播链 | **"真社交"最狠的一击**：你编一条假消息，第二天从别人嘴里听到它 |
| **关系值 / 好感度** | 记录"谁跟谁说过几次"，影响下次转述的措辞 | 信息走样带上**立场**，而不只是变短 |
| **遗忘曲线** | 记忆强度随时间衰减，被重复提到则加强 | 一条信息传三跳后**消失**，而不只是变短 |
| **人格漂移** | 长期对话后人格参数缓慢变化 | ⚠️ **高风险**：漂移不可控会毁掉预设人格。**只做"基调词"级** |

**建议明确不做的三条**（写在这里是为了**防止有人自己去加**）

| 不做 | 为什么 |
|---|---|
| 可追溯漂移日志 | 论文级产物，答辩加不了分，却要改数据结构 |
| 收敛性证明 | 数学证明需要可分析的模型，LLM 是黑盒——写出来是硬凑，一问就穿 |
| 社会科学评测框架 | 需要大规模实验与统计检验，我们的量级撑不起来，**反而暴露规模短板** |

**落到谁头上**（不动附录 C 的分工表，只加不占）

| 机制 | 落到谁 | 为什么不加人 |
|---|---|---|
| `schedule` 日程 + 记忆三因子 + 反思 | **2 号**（引擎线） | 都在记忆 / 对话引擎里，同一份代码，不需要跨人协作 |
| 空闲自语 + 主动性四指标 | **4 号**（主动性 / CV 线） | 复用"主动开口"的既有通道，不出新模块 |
| 信息谱系视图 + 对标表 | **3 号**（前端 / UI） | 纯展示层，只读记忆数据，不碰引擎 |
| 关系值 | 各 NPC 配置的 **owner** | 是**配置字段**，不是功能——写完 JSON 即可 |
