# 保安 · 角色功能与实现

| 项 | 内容 |
|---|---|
| 角色 | 保安 · 老丁（原「保安 · 老丁」人格细化，非新角色） |
| 定位 | **失物招领与报修型智能体** |
| 对标 | 不与谁成对——他是全图唯一的**到场服务** |
| 工具 | `matchLostItem()` + `matchByImage()`【云端】+ `reportRepair()` |
| 版本 | v1.0 · 2026-09-18 |

> 本文档**只写他自身的业务功能与实现**；巡逻、移动、地图图层与主动性载体属地图与行为层，不在本文档范围。

---

## 一、一句话定位

**校园里那个丢了东西能帮你找、东西坏了能帮你报、喊一声就来的保安。**

他最特别的地方有两个：**全图唯一叫得动的角色**，以及手里握着**整个项目仅有的两件真 AI**——**以图搜物**与**证件识别**。

---

## 二、功能清单

### 2.1 失物招领（核心）

**玩家描述得往往不准**——"蓝色的保温杯，上面有贴纸"。所以他不能只靠文字匹配。

| 做什么 | 输出什么 |
|---|---|
| 听懂描述 | 类别（水杯 / 校园卡 / 钥匙 / 耳机…）+ 关键特征 |
| **四维匹配** | 类别 / 地点 / 时间 / 描述关键词，加权求和排序 |
| 返回 | **得分 top-3**，每条带**捡到地点** |
| 认领 | 告诉你"去保卫处认领"——复现现实里的动作 |

**输出要求**：
- **没匹配到就说没有**——他不会编
- **要给"哪条最像"的感觉**，不是甩三条让你自己挑
- **以图搜物命中时，照片的相似度直接接管匹配**（见 §2.2）

### 2.2 以图搜物（**相似度路**）

**描述不清就拍一张。**

| 环节 | 内容 |
|---|---|
| 输入 | 拍照 / 选图 |
| 处理 | 图像编码 → 与失物库向量比对 → 排序 |
| 输出 | 相似物品 **top-3** |
| 训练成本 | **零**——CLIP 零样本，不用训练、不用标注 |

**为什么这是最有价值的一块**：丢东西的人**最大的困难是描述不清**，而照片不用描述。这一条正好补上失物招领最弱的一环。

### 2.3 证件识别与核对（**精确路**）

**校园卡、学生证、身份证这类东西，不需要"像不像"，只需要"是不是"。**

| 场景 | 动作 |
|---|---|
| **入库** | 捡到一张卡 → 拍照 → **OCR 认出学号与姓名** → 以**学号为唯一键**入库 |
| **找卡** | 丢了卡 → 报学号或拍一张 → **精确匹配学号** → 命中即确定 |
| **认领** | 核对卡面信息 → **对得上才给** |

**输出要求**：
- **不是"这三张最像"，是"对得上 / 对不上"**——这是**确定性判定**
- **认错一位就是认错人**——所以必须**双字段交叉验证**（学号 + 姓名）
- **把识别结果念出来让你确认**——"识别到 20231234、张某某，是你的吗？"

> 最后这条不只是兜底：**老丁念出结果让你确认**，既兜住了 OCR 的不确定性，
> 又是一个**人格化动作**——他是在跟你核对，不是在弹一个识别框。

### 2.4 报修

**同一句话，既报修也留档。**

| 步 | 动作 |
|---|---|
| 1 | 玩家说"三教二楼的水龙头坏了" → 命中 `reportRepair` |
| 2 | 抽出**地点**（别称解析 → 落到**自带的点位表**）+ **问题描述** |
| 3 | 生成工单，写入**我自己的工单库**（`visibility: public`） |
| 4 | 别人可以问"我报的修好了吗"——他按地点检索公开条目回答 |

工单记下：**地点、问题、时间、状态、谁报的**。

**不做后台管理端**——工单的"处理"由他在对话里更新状态，**这本身就是一个人格化动作**。

### 2.5 不归他管的

选课、绩点、食堂评分——**一律推走**。

## 三、实现方案

### 3.1 数据：失物库与工单库

| 库 | 每条记什么 | 可见性 |
|---|---|---|
| **失物库** | 类别 / 捡到地点 / 入库时间 / 描述 / **图像向量** | 公共——大家都能查 |
| **工单库** | 地点 / 问题 / 时间 / 状态 / 报修人 | 公共——别人也查得到 |
| **点位表** | 点位名 / 坐标 / **别称**（"三教" = "第三教学楼"） | **自带**——失物招领只用得到常丢东西的地方 |

**两个库都是公共层**：失物招领与报修本质上是**服务全体玩家**的事，写进公共层才成立（设计文档 §18 的异步痕迹）。

> **隔离期的写法**：独立交付时，**公共层就是我自己这两个 JSON**——没有别人往里写，我也没往别处写。
> 合体时这两份文件并入公共层，**我的代码一行不改**。

### 3.2 四维相似度匹配（**他的核心算法**）

| 维 | 判据 | 为什么要有它 |
|---|---|---|
| **类别** | 是不是一类东西（水杯 / 校园卡 / 钥匙 / 耳机） | 先粗筛，避免"保温杯"匹配到"雨伞" |
| **地点** | 丢失地与**捡到地**在**自带点位表**上的距离 | 人在哪丢的，东西多半就在附近被捡到 |
| **时间** | 丢失时间与入库时间隔了多久 | 隔了三天的大概率不是你的 |
| **描述关键词** | 玩家说的话与条目描述重合多少 | 颜色、贴纸、品牌这些**细节特征** |

**四项加权求和 → 排序取 top-3。**

> **权重由 4 号定**（设计文档 §6.3）。
>
> **关键设计**：以图搜物命中时，**图像相似度直接替代"描述关键词"这一维**，
> 其余三维照常参与加权。**照片比描述准得多，但不能把类别、地点、时间丢掉。**

### 3.3 以图搜物：**相似度路径**

**原理**：

```
失物入库 → 顺手算一次 CLIP 向量 → 存库
玩家拍照 → CLIP 编码        → 与库中向量算余弦 → 排序 top-3
```

**两个性能事实**：

| 事实 | 含义 |
|---|---|
| 向量在**入库时**算好 | 检索只是算余弦——**纯 CPU 计算，不用 GPU** |
| GPU 只在编码新图片那一瞬用 | 云端按需开机，不是常驻 |

**链路（不破坏单文件零依赖）**：

```
浏览器（单文件 HTML）        云函数代理（约 30 行）      云端 GPU（按需开机）
  拍照 / 选图      图片 →    注入鉴权 Token     →    CLIP + FastAPI
  base64 编码                转发到 GPU 实例          以图搜图
  渲染候选结果     ← JSON                       ←    top-3 结果
```

**代理层为什么必须存在**：前端不能直连 GPU——跨域、API Key 泄露、HTTPS 混合内容。前端仍是一个 HTML，**只多了一个 `fetch`**；模型在云端，不在包里。

### 3.4 证件识别与核对：**证件 OCR ≠ 通用 OCR**

| 要点 | 做法 | 为什么 |
|---|---|---|
| **只认关键字段** | 姓名 / 学号 / 卡号 | **不整版识别**——字段越少，错得越少 |
| **版式约束** | 校园卡是学校统一版式，字段位置固定 | 按**位置**定位字段，比全文识别准得多 |
| **双字段交叉验证** | 学号命中 **且** 姓名一致，才判"对得上" | **单字段认错一位就是认错人** |
| **置信度门槛** | 低置信度的字段**不参与判定** | 宁可不判，不可误判 |
| **人机协同** | **把识别结果念给用户确认** | 兜住 OCR 的不确定性，且是人格化动作 |
| **拍摄质量** | 提示对准卡面、避开反光 | 卡面反光与磨损是主要错误来源 |

**两条路径的分工（关键设计）**：

| 物件 | 走哪条路 | 判定性质 |
|---|---|---|
| **校园卡 / 学生证 / 身份证** | **OCR 精确核对** | **确定性**——对得上就是对得上 |
| 保温杯 / 雨伞 / 钥匙 / 耳机 | **CLIP 相似度** | **排序**——给出最像的三条，由人认领 |

**为什么必须两条路**：水杯没有唯一标识，CLIP 是唯一的办法；
而校园卡**有唯一标识**（学号），再靠"像不像"就是浪费——**还会把别人的卡排到你前面**。

> **该确定的地方用确定性，该模糊的地方用相似度。**

**隐私口径**：

| 项 | 做法 |
|---|---|
| 入库 | **只落必要字段**（学号 / 姓名），**证件原图用完即弃** |
| 检索 | 靠**学号精确匹配**，不靠照片本身 |
| 不落 | 不做证件照片的长期留存，不做人脸比对 |

### 3.5 技术栈与运行

**① 多模态层**

| 用途 | 选型 | 理由 |
|---|---|---|
| 图像编码与以图搜物 | **CLIP（零样本）** | **零训练、零标注，当天能上线**；演示极直观 |
| **证件文字识别** | **PaddleOCR + 关键字段定位** | **必做**——校园卡、学生证上的学号与姓名要**精确**读出来 |
| **证件比对** | 学号**精确匹配** + 姓名交叉验证 | **唯一键判定**，不走相似度 |

**② 匹配层**

| 用途 | 选型 | 理由 |
|---|---|---|
| 四维相似度 | **加权求和**（类别 / 地点 / 时间 / 文本） | 单一维度都不够可靠，**四维互补才准** |
| 地点维度 | **自带点位表**（几十个常用点位 + 坐标 + 别称）+ 距离计算 | 失物招领只用得到"**常丢东西的地方**"——**不需要全校图谱** |
| 文本维度 | 失物库**关键词匹配** | 量小（几百条），直查即可 |

**③ 服务层**

| 用途 | 选型 | 理由 |
|---|---|---|
| 图像编码调用 | **云函数代理（约 30 行）**——无状态，只做鉴权与转发 | **不算业务后端**；前端不暴露 API Key |
| 云端推理 | **CLIP + FastAPI**，按需开机 | 不常驻，不用时不起 |

**④ 人格配置（设计文档 §6.6 留白处，此处填上）**

```json
{
  "id": "guard",
  "name": "保安 · 老丁",
  "role": "保卫处值班",
  "persona": "公文腔，只讲流程，不寒暄",
  "tools": ["matchLostItem", "matchByImage", "reportRepair"],
  "unknown_line": "这个不归我们管，你去找教务处。"
}
```

> `persona` 这一条**设计文档已明确定死**（"这一条已定，别再改"），本文档只补打招呼与推诿的措辞。

**⑤ 运行形态**

| 项 | 内容 |
|---|---|
| 应答时段 | **08:00–22:00**（设计文档 §6.1） |
| 服务方式 | **到场服务**——全图唯一叫得动 |

### 3.6 为什么这么选（答辩用）

**问：为什么把 CV 用在这两件事上？**

> **零训练、零标注，当天就能上线。**
> 而且它补的是失物招领**最弱的一环**——丢东西的人描述不清，**而照片不用描述**。

**问：已经有以图搜物了，为什么还要 OCR？**

> **两者解决的不是同一个问题。**
> 水杯没有唯一标识——**只能靠"像不像"**，CLIP 是唯一办法；
> 校园卡有唯一标识（学号）——**要的是"对不对得上"**，相似度排序没法回答这个问题，
> 而且**会把别人的卡排到你前面**。**该确定的地方用确定性。**

**问：OCR 认错一位怎么办？**

> 三重保护：① **双字段交叉验证**——学号对上还要姓名也对上；② **置信度门槛**——认不准的字段不参与判定；
> ③ **把识别结果念给你确认**——最后一道防线是人。
> **宁可让你再拍一次，不可把卡给错人。**

**问：为什么要四个维度，不能只用文字匹配？**

> 玩家描述**永远不准**——"蓝色的杯子"可能有二十个。
> 但**地点**（在哪丢的）、**时间**（什么时候丢的）、**类别**（什么东西）都是强信号。
> **四维互补才准；而且照片能直接接管文本那一维。**

**问：为什么检索不用 GPU？**

> **向量在入库时就算好了**，检索只是算余弦。
> GPU 只在"编码一张新图片"那一瞬用，**按需开机，不常驻**。

**问：为什么不做后台管理端？**

> 那会破坏单文件零依赖约束。工单的"处理"由老丁在对话里更新状态——
> **报修不是填表，是跟人说话**，这本身就是一个人格化动作。

## 四、边界

### 4.1 与学长 · 甲

| | 保安 · 老丁 | 学长 · 甲 |
|---|---|---|
| 管 | **失物、报修、门禁**（保卫处的职能） | **校园信息与规则**（空间、流程、时间） |
| **分界** | **丢了东西、东西坏了 → 他** | **问信息、问规则 → 学长** |

**重叠区处理**：问"保卫处在哪"——
- **问位置**是学长/向导的事
- **问失物**是老丁的事

### 4.2 与阿姨 · 丙、算法哥

无重叠——他们管食堂与刷题。

### 4.3 记忆隔离

**老丁记得你报过什么修、丢过什么东西，但其他角色不知道。**

**例外是公共层**（隔离期即我自己的两个 JSON，见 §3.1）——失物条目与工单条目是**公开的**（失物招领和报修本来就该人人可查），
**但对话内容、私密记忆一律不进**。

## 六、独立交付与合体接口

**本角色按隔离开发：数据与实现自包含，可独立开发、独立演示。**

| 项 | 内容 |
|---|---|
| **独立交付件** | ① **登录窗口**——昵称 + 密码，进不去就聊不了；② **聊天界面**——登录后的主界面，失物、找物、报修三个入口都在这里；③ **本角色功能本体** |
| **账号服务** | **轻后端**（FastAPI + SQLite）——注册 / 登录 / 签发 token。**它不是登录 UI 的附属，是「记忆归属」的前提**：有了 `user_id`，记忆才能跨会话、跨设备挂在**同一个人**身上。**本交付件自带一套，独立可跑**；合体时五套并成一套统一账号 |
| **自包含** | 失物库、工单库、**点位表**、匹配算法、图像检索链路——**全部在本角色内闭环**，不依赖其他角色的实现 |
| **唯一的外部约定** | ① 云函数的**转发约定**（不涉业务）；② 合体后**点位表的对齐方式**（我的点位名要能对上大地图的节点）——**都是接口约定，不是实现依赖** |
| **合体方式** | 按总体设计 §2.2 的「工具集 + 人格配置」接入，对外暴露 `matchLostItem()` / `matchByImage()` / `reportRepair()` |
| **合体后** | 引擎读 `tools` 知道他会干什么、读 `persona` 知道他怎么说话——**引擎一行不改** |
