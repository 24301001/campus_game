## 1. 这份交付件是什么（组长新口径）

组长 2025 新要求：**除阿姨外，只交付「简单登录（记住用户名 + 用户历史）+ 简单聊天框，输入内容程序回答」**。

所以本交付件的边界是：

| 层面 | 降级 / 保留 | 说明 |
|---|---|---|
| **UI** | **降级** | 一个登录页 + 一个聊天框 + 历史侧栏。不做完整形象、不做 3D、不做动画 |
| **能力本体** | **不降** | 任务书 §2 的五项能力全部落在服务端：课本问答带出处（真教材 10 本）/ 分步解题（`### 第n步` 步骤卡）/ **拍照提问（📷 图→题面→还是带出处那条链；发出去那条气泡显示的是图）**/ **往年资料（21 份真卷 + 答案区标注 + 同类往年题卡片）** / 复习规划（吃结构统计表 + 章节结构统计）/ 校园信息兜底。`config/tools.json` 里是对外契约 |
| **登录与历史** | 新增（旧任务书没有） | 服务端 SQLite + HMAC 自签 token，按 `user_id` 隔离。记忆是**两层**：原始历史（会话可回放）＋ 归纳出来的画像（跨会话，`backend/memory.py`，口径见 接口契约.md §8） |

一句话：**面子按新要求做小，里子按原任务书做全**。合体时总体设计引擎调的是 `tools.json`，跟 UI 长什么样无关，所以这次降级不影响其他人的模块。

## 2. 架构 A 的数据流

```
浏览器 (web/)                    服务端 (backend/)                  外部
─────────────                   ──────────────────                ─────
登录/注册  ── POST /api/login ─→ auth.py  HMAC 自签 token
                                        db.py   pbkdf2 校验 / 建用户
                                        ├ user / session / message 三张表

输入问题   ── POST /api/chat ───→ agent.py  Agent.run()
   （流式）                        │
                                  ├ ① classify     问题类型（概念/解题/规划/资料）
                                  ├ ② pick_tool    三工具之一（模型 function calling，顺带产出规范术语 terms）
                                  ├ ③ 路由选课     显式选课 > 检索软路由 > 课程清单守卫
                                  ├ ④ search(extra_terms=terms)   BM25 + 向量 → RRF 融合 → 配额 → 精排
                                  ├ ⑤ prompts.py   把命中的课本原文拼成固定前缀
                                  ├ ⑥ llm.py  stream()  ─────────→ LLM API（OpenAI 兼容）
                                   └ ⑦ related()    同类往年真题卡片（只搜 past_paper，排除答案卷）
       ←── SSE 9 个事件: session / meta / citation / retrieval / related / token / done / error / end ──┘
点开角标   ── GET /api/chunk?i=──→ store.by_id()  返回原文 + 页码 + 章节
```

**为什么不是浏览器直连大模型**（架构 B 被否掉的三条硬理由）：

1. API Key 下发到浏览器 = 任何人 F12 就能拿走，按量计费的钱别人花。
2. "记住用户历史"要跨设备，`localStorage` 做不到；多用户下必须服务端存。
3. 索引 108 片可以塞进浏览器，真教材全库不行——现在 **41 577 片**（十本教材 OCR 全文，2026-09-28 起含计网/离散/数据库）+ 向量矩阵，浏览器端塞不下也不算快。

> ⚠️ 原文档 `学霸哥.md` §3.4 写的是"浏览器内 WebGPU + ONNX 真推理"，而同一份文档 §六 要的是
> 「轻后端 FastAPI + SQLite 账号服务」—— 浏览器自己推理就不用服务端检索了，**这两条本身在打架**，
> 得组长书面定一个口径（§13 第 5 条）。
> 但"完全没做"这句现在不成立了：2026-09-27 端上那条路搭起来也量过了。浏览器里真跑
> `bge-small-zh-v1.5` 的 ONNX，和服务端**同一份权重**算出的向量对比：fp32 对 fp32 余弦
> **1.0000000**（最大逐元素差 < 1e-6），int8 对 int8 **0.993–0.9955** —— "推理搬进浏览器"技术上
> 成立，剩下的全是账（Key／历史／审计留多少在服务端、23 MB 权重谁出流量、23 519 片向量塞不进浏览器）。
> 实现与数字见 §6「端上那条腿」，**没接完的那一半**写在 §10 第 31 条。

**两句话的口径**：整页不滚动（聊天窗口占满可视区，消息列表内部滚，输入框永远贴屏幕底）；

检索轨迹全在上面 `#log` 的消息里。

```

＋新对话 │ ⟳刷新 │   │ 三张 │ 你：问题气泡                                  │
历史标题 │ 时间 ⋯│   │ 轮换 │ 她：正文 → 「引用原文 N 条」金边胶囊 → 无出处  │
（0 条…  │ 一行… │   │      │    灰牌 → 同类往年题卡片 → 检索轨迹            │
 提示）  └───────┘   └──────┴───────────────────────────────────────────────┘
```

| **图先进成"字"，再走提问**（默认认完自动问，不用点发送） | ① **出处靠检索**：BM25 和向量都只吃文字，图不转成字就没有 `[n]`、也没有「第186页」，而"页码不许靠模型回忆"是 `prompts.py` 开头钉死的规矩。实测那张例4 截图**全程没人告诉系统它在书的第几页**，识别出的文字一检索，第一条命中就是《概率论与数理统计(第3版)》第186页 第7章假设检验 例4 原文；② **识别会错而且错得很像**：0.515 认成 0.518 模型不会质疑，会照着错数据一路算到底，而这一眼就能看出来 —— 所以那条气泡上**图下面永远折着一行「看识别出的文字」**，点开就是原样题面，认错了一眼看得见（要改就复制出去重问，或取消那个勾退回"先改再发"）；③ **两段延迟分开**：识别约 3 s 有明确的「识别中」，正文照旧流式，不会变成"发张图干等十几秒什么都不出" |
| 视觉模型**跟着主模型走**（`vision.model` 留空） | 实测 `qwen3.8-flash` 自己就吃 `image_url`（一张题目图 188 image_tokens），不必为视觉另开一份 `qwen3-vl-flash` 的账 —— **这是组长 2026-09-22 定的口径**（那个贵）。填成 vl 模型也能跑，同一把 Key，实测识别结果逐字一致，只是另算一份钱：`config/llm.json` 换一行，代码不动 |
| 转写提示词只管「抄对」不管「会做」 | 一字不差、数字/小数点/单位一个不许改、式子写 LaTeX、多小题按原顺序保留题号（例4 / 6.22 那种）；**认不准的字用一个 □ 占位，不许猜一个字填上去**；图不是题目（人像、风景、聊天截图）时只回一行「这不是题目」，后端把它翻译成 400 说给用户 |
| 📷 按钮画不画由后端说了算 | `/api/bootstrap` 带 `vision: {available, provider, model, max_mb}`。`provider=stub`（没 Key）时 `available=false`，前端**不渲染这个按钮**并说明原因，而不是点了才撞一次 500 —— 降级是配置问题，不该让用户先试错 |
| 「拍完直接问」那个勾（`web/index.html` 的 `#shotAuto`） | 组长口径：**拍完直接出答案**，所以识别完**默认自动发出**，少一次点击。三种情况**不**自动发：点「重认」（那是"我要再看看认成了什么"，不该顺手发出去）、输入框里本来就有草稿（那是用户自己写的字，不能替他发）、勾取消了（退回老行为：先落在输入框里改）。选择记在 `localStorage` 的 `xbg_shot_auto`，刷新还在 |
| 认完顺手给一道**同类往年题** | 这不是拍照那条链的新功能，是 §2 第 ⑦ 步 `related()` 本来就会做的事：判据「同一门课 + 同类问法」，只在 `source_type=past_paper` 里搜、**答案卷不进卡片**、最多 2 张。所以**手里有真题的课**（数据库 / 算法 / 软设 / 离散 / 数据结构）拍完题就挂卡片（实测数据结构一张题图挂 2 张，都指到第4页原题）；**高数 / 线代 / 大物 / 概率论有教材没真题 → 一张都不挂**，宁可没有也不拿"教材例题"冒充"往年题"（§13 第 16 条要定这个口径） |
| 气泡上摆**图**，库里存的是**缩略图**（组长 2026-09-22 口径：拍照那条要看图，别摆一长串字） | 发出去那条气泡显示的是这张题图（点开创居中大图，✕／Esc／点图外面都能关），识别出来的文字折在下面一行 —— **字不能删**，出处是靠它检索来的。**存进去的是压过的缩略图不是原图**：前端 `thumbOf()` 压到最长边 900 px、JPEG、≤160 KB（实测 125 KB 那张截图压完 35 755 字），后端 `vision.clean_thumb` 再核一道（mime 白名单 + 长度 + 字符集白名单），**不合格就悄悄丢掉**（气泡退回显示文字），绝不为了它把用户已经发出去的问题打回。落在 `db.message.image`，而 `context_messages()` 压根不选这一列 —— **模型永远看不到 base64**。刷新重开气泡还是图（实测重放后那条 35 755 字与原样一致） |
| 上限挡几处，各说各的话 | 前端 `SHOT_MAX_MB` 挡一道是给"点了才发现太大"的人看的，真判据在服务端 `vision.check_size`（判的是**解码后的字节**，不是 base64 长度）；`/api/vision` 兜一层请求体 16 MB，`/api/chat` 兜一层 2 MB（那条只该出现压过的缩略图，超了就是手滑贴了原图）—— **都在读体之前先看 Content-Length**，不白答一次题 |
| 出错说的话能照做 | `400` 全是图片本身的事，话术里带着动作（"图片 6.7 MB，超过上限 6 MB —— 只截题目那一块就行"／"text/plain 这种图服务商不一定认，截成 PNG 或 JPG 再试一次"）；`413` 请求体过大；`502` 才是服务商那头 |
| Key 仍然只有一处 | `backend/vision.py` 连读都不读 Key，图片经 `LLM.read_image()` 出去 —— 架构 A 那条硬约束（浏览器永远拿不到 Key）没有因为多了一条链而破口 |

旋钮都在 `config/llm.json` 的 `vision` 块：`model`（留空=跟主模型）/ `max_mb` 6 /
`max_tokens` 900 / `max_chars` 4000（转写文本的兜底截断）/ `timeout` 45 s（识别是一次性调用，
不该跟着正文那条 60 s）。端到端实测数字见 §7，HTTP 面见 接口契约.md §7。

## 4. 灌真教材的流程（拿到 PDF 之后，约 10 分钟/本）

> 10 分钟是**带文字层的 PDF**（走 `kb/extract.py`）。**扫描件是另一条路**：本地 OCR 约 6-8 秒/页，
> 一本 300 页 ≈ 30–45 分钟机器时间，见 §4B。微积分上下册＋线性代数＋大学物理学上下册＋概率论与数理统计＋数据结构**七本**都是这么进来的，其中《数据结构》自带文字层，仍要走 OCR 而且必须 `-OcrMode ocr`（见 §4B 表）。

```powershell
# 1) 丢文件（新建 kb\教材\ 目录，按课程分子目录随意）
mkdir kb\教材
# 把 谢希仁《计算机网络》.pdf 一类的文件放进去

# 2) 抽文本（后三个参数必填，book_id 就是切片 id 的前缀）
.\.venv\Scripts\python.exe -m kb.extract "kb\教材\谢希仁计算机网络.pdf" `
    --course 计算机网络 --book "谢希仁·计算机网络(第8版)" --book-id xbg-net8
#   → kb/sources/xbg-net8.md，每段前面带 [page:N] 锚点，自动去书眉页脚
#   复习资料/往年卷加 --source-type outline / past_paper

# 3) 登记一行语料：编辑 config/corpus.json，填 book_id / course / source_type / 形态

# 4) 重建索引
.\run.ps1 -Rebuild
```

**扫描件会报警**：`extract.py` 抽出来文字层 < 50 字/页时判定为扫描件，直接提示需要 OCR。
扫描件要走 OCR 链路，**工时 ×3**（这是任务书 §五 待决项里"教材形态"必须先问清的原因）。

`[page:N]` 锚点是"可点开的出处"的唯一凭依 —— 没有页码，引用就是编的。所以**只接受有文字层的 PDF**。

**六条实测事实（别照抄别人的经验值）**：

| 事项 | 实测 |
|---|---|
| 速度 | 上册 330 页实测 **5.75–8.24 秒/页**（6 批 × 55 页），全程 **41 分钟**。不是「几小时」。**2026-09-21 三本一起跑实测 5.15–20.25 秒/页**（页图多的批次最慢 20.25），872 页合计 **2 小时 02 分**。**2026-09-22 再两本**：概率论 299 页 6.15–9.51 秒/页（6 批合计 36 分钟）、数据结构 343 页 2.41–4.28 秒/页（7 批合计 19 分钟，是强制 OCR 之后的数） |
| **带文字层的书**（《数据结构》那种自带文字层的） | **必须 `-OcrMode ocr`**。auto 一见到真文字层就不做 OCR，改跑纯 Python 的版面重建（docvortex.line_layout），而这本书的代码页一页几百个短行 —— 实测第 2 章那批 55 页 **40 分钟没跑完**（py-spy 抓在 `_infer_text_lanes`），强制 OCR 之后**同一批 132 秒**、整本 343 页 19 分钟。代价：代码里的花括号有认成 1 的，抄代码要对照原书 |
| `-Force` 这个开关是坏的 | 带 `-Force` 重跑时 `-o` 指向**已存在的文件**，MinerU 直接报「当输入为多个文件或目录时，--output 必须是目录路径」——报错和真实原因完全无关（2026-09-22 实测）。重跑前先把旧批次改名挪走，或者让 run_ocr.ps1 在重跑前删掉 `$out` |
| 一本的产出 | 上册 → 317 正文页 / **501,344 字** / 1,779 个独立公式 / **4,089 个切片**（全库从 108 片涨到 4,197 片。2026-09-22 改了超长段的切断规则，这本现在是 4,098 片，§10 第 25 条） |
| 三本新书产出 | 线代 248 页 / 47.6 万字 / 1,398 公式 / **3,113 片**；大物上 292 / 43.3 万 / 1,099 / **2,990 片**；大物下 300 / 43.1 万 / 959 / **2,902 片** → 全库 8,050 → **17,055 片**（建索引 23.7 s） |
| 页码可信度 | 偏移投票：上册 39 个带页码的页 **39 票全一致（偏移 −13）**；入库后 317 页 **页码单调、零重复、逐页对账 0 冲突**。2026-09-21 三本：线代 **241/241 票一致（−15）**、大物上 265/275（−10）、大物下 275/281（−7），入库后都是 1..N 连续无缺页无重号 |
| 「对账不符」不是页码错 | 两本物理书各报 10 / 6 处，**逐条核过是识别器误报**：正文里的编号「式（10-13）」「10.32 如图10-87」被当成了页码，读到的是 2/4/10 这种小数字。偏移由多数票决定，这几页撼不动（对照：线代 0 处） |
| 依赖体积 | 732 MB（4.0 用 onnxruntime，**没有 torch**）。不是 2-3 GB |
| 公式质量 | 可用。`\lim_{x \to 1} \frac{x^2-1}{x-1} = 2.` 这种嵌套结构完整，目测 95%+ |
| 内存 | **必须分批**。可用提交内存 ~4.3 GB 时一把梭会撞 `bad allocation`；跑前 `mineru server stop`（doclib 常驻服务白吃 1.7 GB） |
| 输出格式 | **只用 `--format middle_json`，不要用 markdown**——markdown 里没有页码，而 `[page:N]` 是「可点出处」的唯一凭依 |
| 云端 | **别用 `--remote`**，那会把教材整本上传到 mineru.net |

`kb/middle2md.py` 负责 middle_json -> 语料 .md。四个关键处理，每一个都是被真实数据逼出来的：

1. **页码用「全局偏移投票」，不是逐页识别**：每页有 `page_idx`（全局 0-based）和一个
   `page_number` 块（书印刷页码）。逐页读不可靠 —— 上册 55 页的样张里 **10 页没识别出页码块**，
   逐页 fallback 到物理页码就造出了 `[page:32]` 这种**假页码**（点开和页码对不上，
   出处串号是本项目最严重的一类 bug）。所以改成：把所有阿拉伯页码的「印刷页 − 物理页」
   做多数投票得一个全局偏移，再统一推算每一页。上册偏移 −13、下册 −8，
   **两本不一样，所以只能自动投票，不能手工传 offset**。
2. **封面前置页整页丢弃**：版权页/前言/目录用的是罗马数字（i、viii），和正文的阿拉伯页码
   是两套编号，按偏移推算得出 ≤0 —— 留下就会和正文第 1、2 页串号。上册丢 13 页。
   章节结构不丢（来自每页书眉和正文标题）。`--keep-front` 可强制保留，页码记作 0。
3. **书眉 vs 水印**：一页可能有多个 `header` 块，超星那条
   「北交知行plus 2020学习资源分享群…」就占在书眉位置。原先"取第一个 header"会把整节的
   `chapter` 字段变成一句广告（还会跟着进引用、进向量）。现在按「像不像章节号」挑，
   水印只拦"提升成标题"，正文照原样保留 —— 我们不删语料。
4. **语义级去噪**：`header` / `footer` / `page_number` / `page_footnote` 直接丢，
   比 `extract.py` 那套「跨页重复率 > 55%」的启发式干净；书眉只在**变化时**输出一次当章节标题。

**顺带修掉的两个 `extract.py` 误判**（同一批数据逼出来的，见 `kb/quality.py`）：
判扫描件原来只看「字数 < 40」，**超星的私有编码假文字层每页能"抽出" 300+ 字符**，
整本书一个都没报出来；现在看乱码率（U+FFFD / 私用区占比 > 5% 即判乱码），
并且过半页数是乱码时**直接不写 sources 文件**（宁可不出货，也不建一本假索引）。
书眉长度上限 40 → 80，那条 52 字的群水印才拦得住。

**四个已知损失**：① 图（函数图像、几何示意）不进库——跑的时候加了
`--disable-image-analysis`（省内存），上册丢了 240 个图块，所以「这题的图长什么样」答不了；
② 个别公式识别错（实测把 `p, q` 读成 `\mathcal{P} : 9`），比率很低但不是零；
③ 附录的**习题答案**跟着进库了（上册有 29 页的书眉就是"习题答案"）——
解题辅导会不会被问出答案，见 §10 第 9 条，需要组长定口径；
④ ~~界面上公式显示成 LaTeX 源码~~ **已接本地 KaTeX**（`web/vendor/katex`，0.8 MB，随仓库走、0 公网依赖）。
   认不出的公式**原样显示源码**，不标红也不猜 —— 数学课上把符号显示错比显示成源码更恶劣。

`run_ocr.ps1` 走的是本地推理，**别加 `--remote`**（那会把整本书上传到 mineru.net）；

#### 4C-补：算法 8 份卷子改用 MinerU 逐字识别（2026-09-21 实测）

`kb/papers.py` 走的是**文字层直抽**，对 Word 导出的卷子会栽在公式上：卷面里的
`≤ ≥ × ∈ ①②③ { }` 用的是 Symbol / Wingdings / Cambria Math 字体，PDF 文字层抽出来是
U+E000–F8FF 私用区码位，信息量为 0。实测样本 —— `1≤i≤9` 抽成 `1<U+F0A3>i<U+F0A3>9`、
`s∈{0,1}` 抽成 `s<U+F0CE>{0,1}`、`T(n)=2T(n/2)+n` 整条不见。`kb/quality.py` 的乱码率判据
按**整页**算，368 个乱码摊在 60 页里不足 1%，所以当初判「能入库」没错，只是公式那部分一直是废的。

于是把 §4B 那套 MinerU 用在卷子上（**只对真有毛病的 8 份算法卷**）：

```powershell
.\run_ocr.ps1 -Pdf "E:\...\试卷\算法设计与分析\2023-2024-2-A.pdf" -BookId alg23242a `
    -Course 算法设计与分析 -Book "算法设计与分析 2023—2024学年第2学期期末试卷(A卷)" `
    -Source past_paper -OcrMode ocr -KeepImageAnalysis -Force
```

| 关心的 | 实测 |
|---|---|
| 耗时 | 8 份 / 60 页共 **5.5 分钟**（37–61 秒/份，含模型加载；不用像教材那样分批） |
| 公式 | 私用区乱码 **368 → 0**；LaTeX 公式块 **0 → 496** |
| 正文会不会被 OCR 弄坏 | 中文正文与文字层版相似度 **0.987–0.999**（少字 0–12、多字 3–58，多的基本是符号被认成了字符） |
| 题型/分值统计会不会变 | `map-alg.md` 51 行**逐行一致**，只有 3 处半角逗号→全角（卷面本来就是全角，OCR 更对） |
| 索引 | 17 055 → **17 228** 片 |

三条被实物逼出来的规矩：

1. **`-OcrMode ocr` 不能省。** 默认 `auto` 下 MinerU 对「能取到文字层」的页会直接抄文字层，
   实测残留 38/141（27%）乱码；强制 `ocr` 才归零。扫描教材不受影响（那层是假的，MinerU 认得出来，
   实测 5 本教材 md 私用区字符 0 个），所以**教材不用重跑**，省下约 4 小时。
2. **`kb/papers.py` 现在会绕开 OCR 版**：md 的 front matter 里有 `ocr:` 行就跳过文字层重抽
   —— 否则下次谁跑一遍 `python -m kb.papers`，公式就被换回乱码了。台账 `kb/papers.json`
   记 `"ocr"` 字段；确实要重抽加 `--force`。
3. **数据库 5 份 + 软设 8 份刻意不重跑**：它们的文字层本来就干净（私用区乱码 0），
   OCR 只会把 100% 正确的正文换成有错的识别结果。**「哪份卷子该 OCR」看乱码计数，不看卷子种类。**

还是救不回来的：每份卷 MinerU 会标出 1–9 个**插图块**（流程图 / 示意图 / 递归树），
`kb/middle2md.py` 按既有口径丢弃图片块，所以「如图 3 所示」那种图里的内容仍是空的，只能靠题干。表格里内联的 base64 图片也一起丢（§10 第 25 条）。
想让语料里留下图的位置占位，跑 middle2md 时加 `--figure-note`。

顺带一句：`eval/queries.jsonl` 里那条"洛必达法则"**以前是应拒答用例**（库里没高数）。
入库后它必须有答案，所以已经改成正例，并换了两条真没喂的（特征值/贝叶斯）继续守拒答率。
**2026-09-21 同一件事又发生了一次**：线代入库后「特征值」不再该拒，`none-eigen` 改正例 `lin-eigen`，应拒答位补 `none-cnn`（神经网络——整词和二字成分都 df==0 才算数）；RSA 那条也因大物里出现了「数学原理」而失效，一并换掉。
不改的话，"正确拒答率"这个数字就变成了假的。
**2026-09-22 同一件事第三次发生**：概率论、数据结构入库，`none-bayes` 改正例 `prob-bayes`、`ds-bplus` 从应拒答翻成正例，另补 3 条新书正例（`prob-lln` / `ds-huff` / `ds-inorder`）；两条**失效的**应拒答例子换成「页面置换算法的缺页率怎么算」（操作系统仍零教材），红黑树那条换成「Python 解释器的作者是谁」——红黑树现在已经是数据结构的真主题（#p249-254 好几页），拿它当全库没有的事实去测拒答闸门，测的是个假闸门。

走的是 OpenAI 兼容口（`/chat/completions` + Bearer），所以换服务商只改这三行，代码不动。

### `enable_thinking` 必须关着（实测，同一道题同一个前缀）

| | 思考开 | 思考关 |
|---|---|---|
| 首字延迟 | **18.6 s** | **0.85 s** |
| 输出 token | 951 | 437 |
| 工具路由（非流式） | 10.4 s | 2.1 s |
| 整条回答 | 22.7 s | 14.5 s |

开着思考不只是慢，有两个真坑：

1. `max_tokens` **封不住** reasoning token（实测 `out=976 > max_tokens=900`）——成本不可控；
2. 思考内容在 `reasoning_content` 字段里，正文可能**一个字都不给**。
   `deepseek-v4.1-flash` 实测就是这样：300 token 全花在思考上，`content=""`、`finish=length`。
   所以 `llm.py` 加了护栏：流式跑完还是零正文就抛错说话，**不给你看一条空白回答**。

`extra_body` 是通用透传（只挡 `model/messages/stream/tools/tool_choice` 五个键），
服务商私货参数都往里放，不写死进代码。

### 一条问答的真实成本（实测）

**这两个 token 数是 2026-09-20 四门示例语料下架之前测的**：那条 TCP 题现在没有资料块可喂（四门下架后走 §10 第 1 条说的降级链），
量级还能参考，但已经不是当前口径了。
一次提问=两次调用（路由 + 生成），**路由这一步值不值 2 s 是 §13 可以问的口径**：
现在关键词兜底还在，`route()` 挂了会自动退回关键词，不会整条链死掉。

### 第二条腿已经换成真语义向量了（2026-09-27）

`GET /models` 实测返回 255 个模型，里面有 `qwen3.7-text-embedding-flash` 和 `qwen3.7-text-rerank`。
**接的就是生成层那同一把 Key**，没另开账户、没另要预算：全库 23 519 片重扫一遍约 260 万 token（一块多钱）。
默认值现在是 `embedding.provider: "api"`（512 维，显式传 `dimensions`，不传就是 1024 维、向量文件从 46 MB 变 92 MB）。
三种来源都实现了，也都量过（43 条用例 / top=3）：

| provider | 装什么 | 单条查询 | recall@3 / MRR | 什么时候用它 |
|---|---|---|---|---|
| `api`（**生产默认**） | 无（走 DashScope 兼容口） | **405–763 ms**（中位 ~460，会飘） | 93%（4 次里 3 次）~ 97%（最好一次） / MRR 0.803–0.831 | 不想装本地权重时的选择 |
| `onnx`（CPU·bge-small-zh-v1.5 int8） | `onnxruntime` + 23 MB 权重 | **1–2 ms** | **93%（每次都是这个数）** / **MRR 0.846** | 要可复现、零公网依赖、快；**换词题和 api 打平（都 8/10）** |
| `hash` | 无 | <1 ms | ~~100%~~ / 0.844 | **只给单测当桩**、和线上向量不可用时兜底 |

⚠️ **`api` 那条不可复现，这是今天最意外的一条实测**：同一条查询连调 4 次，3 次逐位相同、
第 4 次 **cos = 0.9990 / 最大逐元素差 6.1e-3** —— 服务商的向量接口不保证逐位一致。43 条里正好有
2 条的期望卡在 3/4 名之间，于是 recall@3 会在 **93% ~ 97%** 之间跳（MRR 0.803 ~ 0.831）。
**所以 97% 不能写进答辩**，要写就写"93%（可复现）/ 97%（最好一次）"。
本地 `onnx` 那条没有这个问题：同一份索引连跑 3 次，**93% / MRR 0.846 / 同样两条红**，一个数字都不飘。
两条腿在换词题上**打平（都 8/10）**，而 onnx 还快 200 倍、不花钱 ——
**要不要把生产默认从 api 换成 onnx 请组长定**（代价：多一个 `onnxruntime` 依赖 + 23 MB 权重，见 §13 第 18 条）。

⚠️ hash 那行的 100% 是**虚高**，别当成"假的比真的准"：那 43 条里「期望片段」往往就是问题原话的出处，
本来就偏字面，字符 n-gram 在这上面占便宜。所以换真向量后头条从 100% 掉到 93%~97% 是**预期内的诚实结果**
（飘红的两条：`prob-bayes` —— 语义路把全概率公式页顶到了《贝叶斯公式的应用》那节前面；
`calc-lhopital` —— **只在抽到坏向量的那几次里红**）。
真正说明差别的是另一套题 —— `eval/run_para_eval.py`，10 条我手写的、刻意不留课本原词的问法：
**A hash w=0.12 → 7　B 拆掉向量腿（纯 BM25）→ 7　C 真语义 api → 8　D C+精排 → 8　E 端上 int8 → 8**。
A=B 那条最要紧：**旧那条 hash 腿在换词题上等于没有**。C 多捞回的是「方程组有没有解看那两个数比一比」这类。
只有 10 条，是方向性证据，**不要当准确率写进答辩**。

**换 provider 之后两个旋钮必须重扫**，这是这次最大的一条教训：`weights.vector` 从 0.12 抬到 **0.25**
（0.12→93%/0.781，0.25→97%/0.831，0.5→93%/0.823，1.0→90%/0.808。**每组只跑一次，而一次抽样的噪声就是 ±1 条 = ±3% recall**，所以 0.25 和 0.5 那点差距别当结论，差 4 条以上才算数 —— 0.25 胜出的依据是 MRR 和换词题那一档，不是 recall 的小数点），`min_cos` 从 0.2 抬到 **0.45**
—— 真向量空间里「查询↔全库最相关片」余弦中位 0.67、「查询↔期望片」0.58、纯噪声 0.001，0.2 那道闸门形同虚设。
这两个旋钮是**按向量空间定的，不是按代码定的**；`engine` 里加了 `_align_vectors()` 看门，
索引里写的来源和配置对不上就报错/就地重算，不许拿两套空间硬乘（§10 第 32 条）。

### 端上那条腿：浏览器里真跑 ONNX（组长 `学霸哥.md` §3.4 要的那个）

**做的程度**：模型真的在浏览器里推理，不调服务端。`web/vendor/xbg-embed.js` 是完整的
Bert 归一化 + 预切分 + WordPiece + CLS/L2 前后处理，权重在 `models/bge-small-zh-v1.5/`。
服务端 `provider=onnx` 走 `backend/retrieval/onnx_embed.py` —— **同一份权重的另一套纯 Python 实现**，
两边互为对照，谁写错都会露。

```
# 0) 取资产（huggingface.co 这边 DNS 不通，走 hf-mirror；ORT 直接下 npm tarball，别 npm install）
.\.venv\Scripts\python.exe tools\get_onnx_assets.py            # 加 --full 连 fp32 一起下
# 1) 三条命令验证，前两条完全离线不花钱
node tools\xbg_embed_check.mjs                                  # 分词 180 条 vs Python 基准，逐 id 比
.\.venv\Scripts\python.exe -m pytest tests\test_onnx_embed.py   # 中文归一/控制符/512 截断/基准向量
powershell -File tools\run_onnx_page.ps1                          # 真浏览器跑一遍，和服务端向量对账
```

**量到的事**：

- **fp32 对 fp32：浏览器和 Python 逐位一致**（cos = **1.0000000**，最大逐元素差 < 1e-6）→
  JS 那条流水线没有实现误差。int8 对 int8 是 **0.993–0.9955**，残余差**全部**来自量化 kernel
  （wasm 的和 onnxruntime CPU EP 不是同一套实现）：Python 侧换 EP、换优化等级结果**逐位相同**，印证了这点。
- 但 0.994 的余弦差不等于名次不动：6 条探测里 top3 **只有 2 条完全一致**（4 条是内部换手），
  top10 重合 8–10/10。所以 int8 端上换的是"顺序偶尔抖"，不是"检索变笨"。
- 全库 23 519 片在 CPU 上离线建向量 **263 s（4.4 分钟）**，产物 48 MB；查询 **1–2 ms**。
  同一套东西评测 93% / MRR 0.846 / **37.5–43.4 ms/条**（对比 api 那档的 404–427 ms），而且**连跑几次 recall 和 MRR 一个数字都不飘**（延迟那部分是机器负载决定的，本地推理本身只有 1–2 ms）。
- **一个都不能信浏览器的 `navigator.gpu` 说法**：`xbg-embed.js` 是先 `requestAdapter()` 探一下，
  探到才把 webgpu 放第一位。无头 Edge 探不到，老老实实报 wasm，此时报"在用 GPU"就是撒谎。

**没接完的那一半（要说清）**：浏览器算出来的查询向量**还没有接进 `/api/chat`**。
它现在是"能自检、能和后端对齐"的状态；要真拿它答题，得给 `/api/chat` 加一个 `qvec` 入参，
并且决定**信不信客户端传来的向量** —— 那等于把拒答闸门的一半交给浏览器，安全上必须组长点头（§13 第 5 条）。
另外 wasm 只能单线程：没有 COOP/COEP 就没有 SharedArrayBuffer，`numThreads=1` 是刻意的（§11）。


### 顺手第三条腿：这把 Key 就有眼睛（拍照提问，§2C）

不用另开 `qwen3-vl-flash` 那份账 —— `qwen3.8-flash` 本身就吃 `image_url`。一张题目截图实测 **2.9–4.0 s、图本身占 188 image_tokens**（整次调用 in≈376 / out≈160 token）。**这是组长 2026-09-22 定的口径：那个 vl 模型贵，不用。** 填成 `qwen3-vl-flash` 也能跑（同一把 Key，实测同一张图逐字一致），换一行 `vision.model` 就行，代码不动。

```json
{"model": "qwen3.8-flash", "temperature": 0.0, "max_tokens": 900, "stream": false,
 "enable_thinking": false,
 "messages": [{"role": "user", "content": [
   {"type": "image_url", "image_url": {"url": "data:image/png;base64,…"}},
   {"type": "text", "text": "把图片里的题目一字不差转写出来…"}]}]}
```

`enable_thinking:false` 在这里**同样要带着**（走的是同一个 `_extras()` 透传）：不传的话实测白烧 42 个 reasoning token。图片以 `data:` URL 直接进请求体，**不落盘**；`/api/vision` 这一侧一个字都不存。

唯一进库的图是**答题那条气泡上的缩略图**（前端压过、≤160 KB，走 `/api/chat` 的 `image` 字段落进 `db.message.image`）—— 它只是显示件，`context_messages()` 不选那一列，模型看不见 base64。

## 8. 检索层设计要点（答辩能讲的都在这）

1. **两路召回 + RRF 融合**：BM25（精确术语）+ 向量（近似语义），`rrf_k=60`。融合的是**名次**不是分数，省掉归一化调参地狱。
   **这条腿的权重改过两次口，两次都是被实测逼的**。第一次（hash 时代）压到 0.12：学生问「洛必达**准则**」
   （书上写的是「法则」），hash 按字面相似把「2.5 极限存在准则」「11.1.3 柯西准则」顶到第 1、2 名，
   正主 6.2 反而掉出前三，模型照着资料回一句「课本里没有」；当时扫 12 组，recall@3 在 ≥0.05 全程 100%，
   换词那条**只有 ≤0.12 才修好** —— 因为那个"向量"是假的，所以不给它排序话语权。
   第二次（2026-09-27 换成真语义向量之后）重扫，**0.25 才是新的甜点**（93%~97% / MRR 0.803~0.831；
   0.12 只有 93% / 0.781，0.5 是 93% / 0.823，1.0 掉到 90%），同时 `min_cos` 从 0.2 抬到 0.45：
   真向量空间里噪声片余弦就在 0.0 附近，0.2 那道闸门形同虚设。
   **教训**：`weights.vector` 和 `min_cos` 是**按向量空间定的，不是按代码定的**，换 provider 必须重扫，
   所以 `engine` 里加了 `_align_vectors()` 看门 —— 索引自报的来源和配置对不上就报错或就地重算，不许硬乘。
2. **虚词闸门**：`的/是/有/什么` 这类 df > 35% 的词不参与打分，否则"什么是X"永远命中所有含"什么"的段落。
3. **专有词闸门 `unknown_terms`**：问题里出现 ≥3 字、非疑问功能词、且 **df==0** 的词 → 判"这门课没喂"，**直接拒答**。这是正确拒答率 100% 的来源，也是"绝不用记忆补"的技术兑现。
4. **`_informative` 必须先取"库里存在的词"**：否则过滤完是空集，零命中被误判成"低置信"，其实是"根本没法判"。
5. **分库配额在融合之后做**（带回填）：融合前配额会让某一本书的独占高分片段没有比较基准。
6. **类型先验是名次惩罚不是分数相乘**：提纲/往年卷原样抄着题目本身，字面匹配度天然高于讲答案的正文，`source_prior` 给 outline 0.72 / past_paper 0.68。
7. **暴力余弦，不用 FAISS**：23 153 片实测 6.0 ms/次（17 055 片 5.2 ms、8 098 片 2.1 ms、108 片 0.4 ms，线性涨）。
   ⚠️ 这是**点积那一下**的账。整条 `search()` 在 `provider=api` 下还要加一次查询向量调用（405–763 ms，见 §6），别拿这句去解释实测的 500 ms；要个位数毫秒就 `provider=onnx`。
   10 万片以内 `numpy` 矩阵乘都够快，加 HNSW 是**负收益**（召回还下降）。超过 10 万条再换。
9. **给模型的课程举例清单从语料生成，不手抄**（`Agent._course_examples`）：手抄那份没有「大学物理」，大物入库当天「熵增加原理/卡诺循环/库仑定律」三问全被报成 高等数学，检索真给出 5 条微积分的页当资料——这就是第 2 条那句「比拒答坏得多」的活标本。
8. **索引热重载**：`store.maybe_reload()` 按 mtime 判断，重建索引不用重启服务。
9. **归一术语 `terms`**（route() 顺带产出，**只喂字面路**）：学生说「准则」书上写「法则」、说「夹着算」
   书上写「夹逼 / 单调有界准则」，字面检索就扑空 —— 和用户那张截图是同一个根因，上次靠压权重治的，这次走正路。
   让**本来就要跑的那一次** function calling 顺带给出 2~4 个规范说法，追加进 BM25 查询词。四条边界一条不松：
   ① 不新开调用（实测 route 1.5–2.7 s，加 terms 只多约 0.3 s）；② **原话一个字不改**，terms 只做追加；
   ③ 只喂 BM25 —— 向量路、`coverage`、`unknown_terms` 两道拒答闸门继续**只看原话**，否则模型补一个词就能把
   "这门课没喂"洗成"喂过了"（`test_coverage_and_refusal_gate_read_only_the_original_words` 钉住这条）；
   ④ 模型给的词过**词表真值闸门**：`df>0` 才收，复合词（`B+树` 要先 normalize、`单调有界准则` 拆成分）
   退回按成分查，再不行找包含它的索引词；查无此词的进 `dropped_terms`，前端挂灰胶囊如实写"丢"。
   效果见 §7 两行对照（recall@3 100% vs 88%）。为什么**没有**再加一层"只收有判别力的词"：见 §10 第 21 条。
10. **课程是硬约束，资料类型是软约束**：低置信时只允许放宽 `source_type`，**不允许跨课程捞**
    （判据是 `agent.run()` 里的 `given` 标志）。这条是四门示例语料下架当天撞出来的：「数据库四种隔离级别」
    → 数据库没教材 → 老代码放宽到全部课程 → 引《微积分上册》第 N 页当出处。看着比拒答体面，
    其实是把两门课缝在一起瞎答。`given` 区分的是**课名是谁说出来的**：用户原话或模型点名的课不许放宽
    （认错了就老实说没有）；软路由按检索分布自己猜的课可以放宽（本来就是猜的，不许拿猜的结果把用户堵死）。
    同一个地方还修了两条：① 路由参数明写**缩写不许让模型补全成整门课名** —— 实测同一句「软测的期末会怎么考」
    一次引到真卷、一次回"没这门课"，掷硬币的根源就是模型一会儿写「软件测试」一会儿写「软件设计与分析」；
    ② 真对不上时**只建议不改判**：`_suggest_course()` 在字符重合度之外加**共有前缀**（软件 / 数据 / 概率），
    「软件测试技术」六字只重合 2/6，本来够不上门槛，实测兜底话术就退化成干列一遍课程清单；
    现在那句是「你说的会不会是《软件设计与分析》？那门我手上有往年卷 8 份、题型结构 1 份」，整条 98 字。

## 9. 多本书怎么做（三道路由，不做前置强制分类）

结论：**不要在检索前面加一个"先判断是哪本书"的分类器**。三个理由：

1. 分类错了不可恢复 —— 后面检索在错误的库里找，永远找不回正确答案，而且**错得很自信**（低置信信号都没了）。
2. 跨教材对比（`cross_book`，任务书 §2.1 明确要的能力）直接被废 —— 只允许一个库。
3. 多一次模型调用 = 多 300–800 ms 和一份钱，买回来的是个会出错的负收益。

实际实现是三路混合，优先级从高到低：

| 顺序 | 路由方式 | 代码 | 行为 |
|---|---|---|---|
| ① | **用户显式选课** | `agent.run(course=...)` ← 页面课程 chips | 最高优先，直接 `course=` 过滤 |
| ② | **检索分布软路由** | `agent._soft_route()` | 全库检索一次，看 top 命中集中在哪门课，据此**收紧**再查一遍。不集中就保持全库 |
| ③ | **课程清单守卫** | `agent._hit_course()` + `unknown_terms` | 问题提到"高数"但库里没这门课 → 走 `persona.兜底话术.没这门课` 直接兜底，不硬答 |

书越多越要关心的只有一个旋钮：`retrieval.json.per_book`（每本最多占几个坑）。默认 3，`cross_book=true` 时改成 1（每本各留一条）。
加到 10 本书、每本 5000 片，暴力余弦大约 50k×512×4B ≈ **100 MB 内存 / 单次约 5–10 ms**，仍然不需要向量库。

## 11. 部署到服务器

```
用户浏览器 ──443──> nginx ──/api/*──> uvicorn 127.0.0.1:8010 ──> LLM API
                          └─ / 静态 web/
```

1. `deploy/nginx.conf` 抄过去改 `server_name`。**关键一行是 `proxy_buffering off;`** ——
   不关缓冲，SSE 会被 nginx 攒成一块，流式变成"憋 3 秒一次性吐完"，用户体感直接崩。
2. `uvicorn` 用 systemd 或 `nssm`（Windows 服务器）常驻，**别开 `--reload`**（那是开发用的）。
3. 多 worker 注意：索引在进程内各持一份 —— 当前 **23 519 片 + 48 MB 向量**，实测常驻工作集 **278 MB**
   （2026-09-27 量的；8 098 片那会儿是 169 MB，多出来的主要是 512 维 × 片数那份 float32 矩阵）。
   要么 `--workers 1` + 靠异步扛并发，要么接受内存倍数（真教材再翻几倍时就必须算了）。
4. `data/`（SQLite + `.secret`）在服务器上是**唯一状态**，备份它。`.secret` 丢了所有人的 token 失效（要重登）。
5. Key：服务器上**只用环境变量** `XBG_LLM_KEY`（systemd `Environment=` 或 `EnvironmentFile=`），
   不要把本机的 `data/.llm_key` 拷上去，也不要填进 `config/llm.json`（那文件要跟合体仓库走）。
   **永远不进 git、不进浏览器**。换 Key 只需重启服务，`GET /api/health` 会报 `key_present`。
   同一份 `/api/health` 现在还报 `rerank`（provider / 调用次数 / 失败次数 / 平均 ms）和索引自报的
   `embed_provider` / `embed_dim` / `vector_docs` —— **关着要说是关着，别看代码看着像坏了**。
6. **`provider=onnx` 或端上那条路才需要的资产**：权重目录 `models/`（`MODELS_DIR`）挂在 **`/models`** 上，
   目录不存在就不挂这条路由，不影响其它端点。int8 22.9 MB / fp32 94.9 MB，再加 ORT-Web 那份 wasm 20–45 MB，
   **首访流量按 45–140 MB 算** —— 公网要么上强缓存头，要么干脆别开（生产默认是 `api`，不碰这块）。
   ⚠️ Windows 上 `.mjs` 的 MIME 常被注册表猜成 `text/plain`，浏览器会**拒绝 `import()`**：
   `app.py` 里已经 `mimetypes.add_type("text/javascript", ".mjs")` + `application/wasm` 钉死，
   走 uvicorn 或反代到它都对；只有把 `web/` 直接丢给 IIS 静态托管才需要另配站点级 MIME。
7. **wasm 想多线程就得给 COOP/COEP**：没有 `SharedArrayBuffer` 就没有线程池，所以 `xbg-embed.js`
   现在固定 `numThreads=1`。要开线程得全站上 `Cross-Origin-Embedder-Policy: require-corp` +
   `Cross-Origin-Opener-Policy: same-origin`，那会把没有 CORP 头的第三方资源一起挡掉 —— **这版故意不做**。

**瓶颈仍然在 LLM API 的 TTFT，不在服务端**：一条问答的首字 2.6–3.2 s 里，模型选工具就要 1.8–2.2 s，
其余全是模型那边的（`enable_thinking` 关掉后的数字，见 §6）。
**但"检索这一段是零成本"这句话现在要说清条件**：换成真语义向量（`provider=api`）之后，检索这一段
从 7.3 ms/次 变成 **404–427 ms/条**（预热实测 516 ms/次，大头是那次查询向量的外部调用，它自己就在
405–763 ms 之间飘），hash 时代那些个位数毫秒**不再成立**。整块仍然藏在模型那两三秒里面，
**用户体感没有变化**，但超时和并发账要按新的数算。要把它压回 1–2 ms 并且可复现，就把 provider 改成 `onnx`
（37.5–43.4 ms/条含全部本地计算，零公网依赖）；`--rerank` 再另加 461 ms/问，所以默认关。
**部署侧要优化的仍然不是性能，而是并发（见上面 worker 那条）和超时（nginx 读超时 ≥ 60 s）。**

## 12. 环境坑（我这台机器踩过，换机器会重现）

- **C 盘满**：pip 装包会 `No space left on device`。解法：
  ```powershell
  $env:TMP=$env:TEMP='E:\项目\第五学期\软测\xueba-ge\.tmp'
  .\.venv\Scripts\python.exe -m pip install -r requirements.txt --no-cache-dir
  ```
  （`.tmp/` 已在 `.gitignore`，用完可删）
- **外网直连不通**：走代理 `http://127.0.0.1:7897`
  ```powershell
  $env:HTTP_PROXY=$env:HTTPS_PROXY='http://127.0.0.1:7897'
  git -c http.proxy=http://127.0.0.1:7897 clone ...
  ```
- **控制台中文乱码**：`[Console]::OutputEncoding=[System.Text.Encoding]::UTF8; $env:PYTHONIOENCODING='utf-8'`
- **KaTeX 资源哪来的**：`web/vendor/katex/` 是 `npm pack katex@0.16.11` 解出来再删剩的
  （只留 `katex.min.js` / `katex.min.css` / `fonts/*.woff2` + `*.woff` 兜底 / LICENSE，实测 0.82 MB）。
  换机器不需要重装 node：这堆文件跟着仓库走，**服务不联网也能渲染公式**。
  真要升级版本：
  ``cd web\vendor && npm pack katex@latest && tar -xzf katex-*.tgz``，
  把 `package/dist/{katex.min.js,katex.min.css,fonts}` 拷出来即可。
- **端上那套权重的来源**：`huggingface.co` 在这台机器上 DNS 直接不通，`tools\get_onnx_assets.py` 走
  **hf-mirror.com**，而且**必须带 `User-Agent`**（不带就 403）。ORT-Web 那份别再 `npm install` 了 ——
  这台机器上跑了 20+ 分钟最后把 node_modules 回滚了，脚本改成**直接下 tarball 再 `tar -xzf` 抽两个文件**。
- **无头浏览器量端上必须换全新的 `--user-data-dir`**：`.mjs` 会被缓存，不换 profile 你测到的是上一版脚本，
  表现就是"改了没生效"。另外无头 Edge 的 `navigator.gpu.requestAdapter()` 返回 null → 它如实报 **wasm EP**，
  而 `--virtual-time-budget` 之下 `performance.now()` 出来的毫秒数**没有意义**（延迟要在真浏览器里量）。
- **PowerShell 里 `python -c "...$y$..."` 会把 `$` 当变量吞掉**：探针一律写成 `.py` 文件再跑。
  这次量 tokenizer 就被咬过一次 —— `$y$` 变成空串，看起来像分词器的 bug，其实是 shell。
- **原生命令的 stdout 有时候回不来**（msedge 那次捕获到 0 字符）：`| Out-File` 落到临时文件再读，
  并且把 `$ErrorActionPreference` 设回 `Continue`，Edge 爱往 stderr 写噪声，`Stop` 会整条中断。
- **别用 `apply_patch` 之外的方式猜文件换行**：本仓库文件 `newline` 不统一（有 `\r\n` 有 `\n`），改文件要逐文件探测。
