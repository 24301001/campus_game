# 阿姨 · 角色功能与实现

| 项 | 内容 |
|---|---|
| 角色 | 阿姨 · 丙（原「阿姨 · 丙」人格细化，非新角色） |
| 定位 | **食堂口碑与窗口查询型智能体** |
| 对标 | 与向导 · 小北互补——他管**怎么去**，阿姨管**值不值得去** |
| 数据 | 人工整理档口库 ＋ **校园墙离线采集** ＋ 玩家众包 |
| 版本 | v1.0 · 2026-09-18 |

---

## 一、一句话定位

**校园里那个站在窗口后面、知道哪个窗口好吃、哪道菜值得排队的阿姨。**

她管的是**全校食堂的活口碑**——口碑不是一张静态评分表，而是**有发布者、会随时间变旧**的东西。开学时夸上天的窗口，换了厨师就该重新评价。

她还把这份口碑**画出来**：每个食堂的两层平面图，档口上直接标菜名、价格、评分（见 §2.5）。**问她是一个入口，看那张图是另一个入口。**

---

## 二、功能清单

### 2.1 窗口与菜品查询（骨架）

**她能报出的事实**——来自人工整理的基础库：

| 问什么 | 答什么 |
|---|---|
| **有哪些窗口** | 食堂 / 楼层 / 窗口名（"学二三层""三窗口"） |
| **卖什么** | 每个窗口的固定菜品清单 |
| **多少钱** | 价格（**人工核对**，不靠爬） |
| **几点开** | 营业时间 |
| **在哪** | 在地图上的位置（可联动高亮） |

**输出要求**：
- **必须准**——价格与营业时间是**事实**，不准比不答更糟
- **答得出"窗口级"的**：这个窗口几点开、在哪；**答不出"校园级"的**：图书馆几点开（见 §四）

### 2.2 口碑问答（核心）

| 玩家问 | 阿姨怎么答 |
|---|---|
| **"哪个窗口好吃"** | 报出加权得分最高的窗口 + **她自己的转述口吻** |
| **"三窗口今天排队吗"** | 依据**最近几小时**的条目回答 |
| **"麻辣香锅哪家强"** | 按**菜品**维度的口碑排序 |
| **"二食堂有什么"** | 骨架库精确查（这是事实，不是口碑） |

**输出要求**：
- **带立场**——她不是念数据，是"我跟你说，三窗口那个香锅是真香，就是队排得长"
- **没数据就说不知道**——**她不会编**
- **会变旧**——旧评价权重随时间衰减，不压着新评价

### 2.3 排队与实时状态

- 依据**最近几小时**的条目判断哪个窗口在排队
- 数据来源同样是玩家的话（"刚排了二十分钟"）
- **没有近期数据就不答**，不做推测

### 2.4 榜单与校园地图图层

| 形态 | 说明 |
|---|---|
| **对话** | 主形态——用口语转述，带她的立场 |
| **榜单卡片** | 问"哪个窗口最好"时输出排序，卡片式贴进气泡 |
| **校园地图图层** | 把有口碑数据的窗口在**校园大地图**上高亮 |

### 2.5 食堂两层档口像素地图（**本节新增交付**）

**从"哪个窗口好吃"到"一眼看见哪个窗口好吃"。**

把每个食堂的**两个楼层**画成像素平面图，每个档口是图上一块像素块，
块上直接标**菜名、价格、评分**——口碑从"要问才知道"变成"**扫一眼就看见**"。

**三个"一眼"**：

| 一眼看见 | 靠什么 |
|---|---|
| **哪些窗口在哪** | 档口的**平面位置**与**占地大小** |
| **哪个窗口好** | 档口块的**底色**（评分色阶） |
| **贵不贵** | 紧跟菜名后的**价格数字** |

**形态**：

| 要素 | 怎么呈现 |
|---|---|
| **楼层** | **两层各一张平面图**，上下切换（不做立体楼梯） |
| **档口** | 像素块，大小按**真实占地面积**等比 |
| **菜名** | 档口块的**主标签**——默认显示招牌菜 |
| **价格** | 紧跟菜名后的数字（招牌菜的价格） |
| **评分** | 档口块的**底色**——越好越暖，见 §3.4④ |
| **评论** | 点档口 → 弹出该档口的菜品清单 + 评分 + 评论列表 |

**关键设计：评分不做成数字，做成颜色。**

> 像素画里画星星又丑又占位，数字要读，**只有颜色能一眼扫过去**。
> 这就是把口碑做成一张**热度图**——哪个窗口红、哪个窗口灰，不用问。

**输出要求**：

- **底图静态、档口数据驱动**——装修图画一次，档口层跟着口碑刷新
- **口碑变了颜色跟着变**——地图是**活**的，不是一张截图
- **没数据的档口显灰，不显假**——**宁灰不假**，灰是"还没人评"，不是"差"

**交互**：

| 动作 | 结果 |
|---|---|
| **进** | **隔离期**：从聊天界面直接选食堂打开；**合体后**：校园地图上点食堂进入 |
| **切层** | 一层 / 二层 两个按钮（或图上的楼梯图标） |
| **点档口** | 浮出该档口的菜品、价格、评分、评论 |

**分界（重要）**：

| 问什么 | 归谁 |
|---|---|
| 校园里"食堂在哪、怎么走" | **向导 · 小北** |
| 食堂里"**哪个档口好**" | **阿姨** |

> 内视图的**主体是口碑可视化，不是寻路**——所以它归阿姨，不归向导。
> 它只是把"阿姨知道的事"画出来了。

### 2.6 阿姨的人物建模（**交付项**）

**她得先有个人样。**

食堂地图是**场景**，她是**站在场景里的人**。这一节交付的是**阿姨本人**——
一个能在像素校园里走动、站着、说话的角色精灵。

**交付什么**：

| 项 | 内容 |
|---|---|
| **像素精灵** | 四向（上 / 下 / 左 / 右）× 行走帧 + 站立帧 |
| **形象** | 围裙、套袖、头巾——**一眼认出是食堂阿姨**，不与学生 NPC 混淆 |
| **站位** | 饭点站在窗口后面（位置由 §3.4 的档口 `rect` 给出） |
| **说话** | 对话时头顶出气泡，精灵切到"说话"帧 |
| **朝向** | 玩家走近时**转向玩家**——最省事的"她注意到你了" |

**为什么人物建模归她**

> 食堂的档口是她画的，站在档口后面的**也得是她**。
> 两个人分头画场景和人物，**比例、描边、配色必然对不上**——
> 像素风里这种不统一**一眼就能看出来**。

**与食堂建模的关系**：

| | 食堂建模（§2.5） | 人物建模（§2.6） |
|---|---|---|
| 是什么 | **场景**——她站在里面 | **角色**——站在场景里的人 |
| 动 / 静 | 基本静态（只有口碑变色） | **一直在动**（待机、转身、说话） |
| 渲染层 | 底图层 + 档口层 + 标签层 | **角色层**（在档口层之上、标签层之下） |

**输出要求**：

- **她的位置由档口决定**——站在自己主管的窗口后面，不是随便摆
- **不抢戏**——她是个会说话的窗口，不是主角；精灵尺寸与 NPC 学生**同规格**
- **待机不能是静止帧**——至少要有呼吸 / 摆动的两帧循环

### 2.7 打分：说话即打分（**没有打分 UI**）

**玩家不需要填表单**——打分是说话的一部分：

> "三窗口的麻辣香锅不错，就是排队久" → 自动落成一条口碑

**这一条是产品主张，不能破**：玩家不需要知道"功能菜单在哪"，他只需要**走到这个人面前说话**。

### 2.8 不归她管的

选课、绩点、失物招领、图书馆规则——**一律推给别人**（见 §四）。

## 三、实现方案

### 3.1 数据来源：**三层**（本文档的核心）

阿姨的数据不是一种东西，是**三种来源、三种性质、三种更新节奏**：

| 层 | 内容 | 来源 | 产物 | 更新节奏 |
|---|---|---|---|---|
| **① 档口与菜品库**（骨架） | 食堂 / 楼层 / 窗口 / 菜品 / **价格** / **营业时间** / 位置 | **人工整理** | `canteen.json` | 学期初整理，随变动改 |
| **② 口碑底料**（冷启动） | 校园墙上关于食堂的公开发言 | **离线采集**（校园墙） | `reviews_imported.json` | **一次性**抓取，之后自然衰减淡出 |
| **③ 口碑主流**（长期） | 玩家说话时留下的评价 | **众包**（对话中产生） | `reviews.json` | 持续增长 |

**为什么骨架必须人工整理**

价格和营业时间是**事实**，校园墙上的发言零散且过时，**爬不出可靠答案**。而这恰恰是"三窗口贵不贵""几点关"这类问题的唯一答案来源。好在量不大——几个食堂 × 十几个窗口，**一次整理，一学期受用**。

**为什么底料要爬校园墙**

众包有**冷启动问题**：上线第一天没人说过话，阿姨对任何问题都只能答"不知道"。

校园墙是**本校学生自己的公开言论**，比第三方平台更贴近真实体验，而且**天然带校园语境**——"学二""三窗口""学一地下"这些简称，只有校内人才懂，第三方平台的评价根本不会这么写。

**爬虫的形态：离线工具，不进交付物**

```
校园墙公开内容
  → 抓取（限速·只抓公开页）
  → 筛出食堂相关（关键词：食堂 / 窗口 / 菜名 / 简称）
  → 抽取成结构化口碑（LLM 离线批处理）
  → 去重 · 去广告 · 去个人信息
  → 落成 reviews_imported.json
```

**运行时一行爬虫代码都没有**——这和"课本离线切片"是同一个模式：**重活离线做完，运行时只有查询。**

**底料是垫脚石，不是长期数据**

底料条目**没有"谁说的"**，不该和本校学生的真实体验同权。它带 `source: imported` 标记、走**更低的来源权重**，玩家贡献量上来后**按衰减曲线自然淡出**，不需要人工删。

### 3.2 口碑怎么变成分数

每条口碑记下**六样**：哪个窗口、几星、说了什么、有什么标签、什么时候、**谁说的（来源）**。

**窗口得分 = Σ(星级 × 权重) / Σ权重**，权重由两个因子相乘：

| 因子 | 作用 |
|---|---|
| **时间衰减** | 旧评价变淡——换厨师、翻新之后，开学时的好评不该继续压着新评价 |
| **来源权重** | 玩家贡献 > 采集底料（本校学生的真实体验优先） |

> ⚠️ 别和**记忆检索**的时间因子混：记忆走的是 `recency × relevance × importance`，
> 口碑走这条**独立衰减曲线**。

**标签体系**是这一层的骨架：口味（辣/清淡）、分量、价格、排队、环境。标签让"哪个窗口好"能按维度拆开答。

### 3.3 她怎么回答

```
玩家的话
  → 意图分类（问好吃 / 问排队 / 问菜品 / 问价格 / 闲聊）
  → 取数
      问口碑  → 读我自己的口碑库，按权重算分或排序
      问事实  → 查骨架库（精确匹配）
      问排队  → 取最近 N 小时的条目
  → LLM 转述（带她的口吻与立场）
  → 气泡渲染（榜单则出卡片）
```

**两条硬规则**：
- **没有数据就说不知道**——她不会编
- **不是口碑范畴的推给别人**——不越界

### 3.4 食堂两层像素地图：数据模型与渲染

**① 数据模型（`canteen.json` 的扩展）**

```json
{
  "canteen": "学二",
  "floors": [
    {
      "level": 1,
      "size": [32, 20],
      "stalls": [
        {
          "id": "x2-1-03",
          "name": "三窗口",
          "rect": [12, 6, 8, 4],
          "dishes": [
            { "name": "麻辣香锅", "price": 14, "signature": true },
            { "name": "酸辣粉",   "price": 10 }
          ]
        }
      ]
    },
    { "level": 2, "size": [32, 20], "stalls": [] }
  ]
}
```

三条设计：

| 设计 | 为什么 |
|---|---|
| `rect` 用**格坐标** `[x, y, w, h]`，不用像素坐标 | 与像素格对齐，**缩放不糊**；改分辨率不用重标 |
| 两层是**两个独立平面**，不做三维 | 像素风里做三维室内是**负收益**——画不像、看不懂、还贵 |
| 底图与档口**分开存** | 底图静态（装修），档口**数据驱动**（口碑）——只有后者会变 |

**② 坐标从哪来：人工量**

对着食堂的真实平面图（或现场走一遍），**按格子描**。

- 工作量：几个食堂 × 两层 × 十几个档口
- **一次性**，只在装修/档口变动时重标
- 这也是**唯一**需要人的地方——其余全是数据驱动的自动渲染

**③ 渲染：三层分离（Canvas 2D）**

| 层 | 画什么 | 刷新频率 |
|---|---|---|
| **第 1 层 底图** | 地板、墙、通道、桌椅 | **烘焙一次，缓存**（离屏 Canvas） |
| **第 2 层 档口** | 档口块，**底色 = 评分色阶** | 数据变化时重绘 |
| **第 3 层 标签** | 菜名 + 价格 + 热区 | 跟着第 2 层 |

> **底图必须烘焙缓存**：底图不变，每帧重画是纯浪费。
> 主循环里每帧只重绘"会变的那一层"——和校园地图的做法一致。

**④ 评分 → 色阶：5 档离散**

```
4.5 – 5.0  ●  暖橙
4.0 – 4.5  ●  浅橙
3.5 – 4.0  ●  米黄
3.0 – 3.5  ●  灰蓝
< 3.0      ●  深灰
无数据      ●  中性灰（描边区分）
```

**必须离散分档，不要连续渐变**——像素风里连续渐变反而**糊成一团**，
5 档的色块边界清晰，一眼能数出"哪几个是红的"。

**"无数据"必须与"差"在视觉上分开**：中性灰 + 虚线描边，
否则新窗口一上来就是深灰，等于**被地图判了死刑**。

**⑤ 标签防重叠（最实际的技术点）**

十几个档口挤一层，菜名四个字起（"麻辣香锅"），**必然压**。三级降级：

| 级 | 做法 | 何时用 |
|---|---|---|
| **1 缩** | 只显示**招牌菜**，长名截断加省略号 | 块宽放得下就到此为止 |
| **2 避** | 标签**外移**到块外，加引线指回档口 | 块内放不下时 |
| **3 藏** | **只留评分色块，不显示文字** | 空间实在不够时；点开才出全名 |

> **优先级：块内 > 引线外移 > 只留色块。**
> **宁可少显示字，不可让字叠在一起**——叠字比不显示**更糟**。

**⑥ 两层切换**

- 一层 / 二层两个按钮，或地图上的**楼梯图标**
- 切换时**上下对应的档口位置要能对上**（同一竖列的两层，视觉上连续）
- **层高不画**——两层就是**两张平面图**，用按钮和标签区分

**⑦ 数据刷新：这是"活地图"的关键**

```
玩家说 "三窗口香锅真香"
  → 落一条口碑 → 重算该窗口得分 → 档口底色变暖
```

**口碑一进来，地图就变。**这就是它和一张静态截图的分水岭——
**地图是口碑的显示终端，不是一张宣传图。**

### 3.5 阿姨的人物建模：从精灵图到站位

**① 精灵规格**

| 项 | 规格 | 为什么 |
|---|---|---|
| **尺寸** | 与校园现有 NPC **同规格** | 不同规格在轴测图里**比例一眼就不对** |
| **朝向** | 四向 × 各 2–4 帧行走 + 1 帧站立 | 满足基本动作，**不做八向** |
| **锚点** | 沿用现有 `ax` / `ay` 约定（**脚底中心**） | 与地图的碰撞盒、遮挡排序对齐——不然她会浮空、或被建筑挡错 |
| **风格** | 与校园美术一致：**实心色块 + 深色描边** | 不引入新的画风 |

**② 为什么是四向，不是八向**

> 轴测图里八向的斜向帧**要多画一倍**，而玩家**几乎注意不到区别**。
> 四向够用——把省下的功夫花在**待机动画**上更值。

**③ 站位：由档口算出来，不是手摆**

```
档口 rect → 取窗口前沿中点 → 转成精灵锚点 → 她站那儿
一层 / 二层切换 → 对应层的站位跟着切
```

> **她不是被摆在地图上的，是被档口"放"在那儿的。**
> 档口一挪，她跟着挪，**不需要重标**。

**④ 动画状态机**

| 状态 | 触发 | 表现 |
|---|---|---|
| **待机** | 默认 | 两帧循环（呼吸 / 轻晃）——**不能是静止帧** |
| **转向** | 玩家走近 | 翻到面向玩家的那一向 |
| **说话** | 对话中 | 切"说话"帧 + 头顶气泡 |
| **行走** | 预留 | 四向行走帧——**本文档只建模，移动属行为层** |

**⑤ 遮挡排序**

和建筑、档口一起按 `baseY` 排序：站在档口前**盖住档口**，站在建筑后**被建筑盖住**。

> 用现有的排序约定即可——**这也是为什么要沿用同一套锚点**。

**⑥ 与地图的分工**

| 项 | 归属 |
|---|---|
| **本文档交付** | 精灵图、动画帧、状态机、站位计算 |
| **接口约定（不属本文档）** | 她**什么时候出现**（饭点）、**怎么被叫住**——属行为层 |

**⑦ 这轮建模立下的规矩（后续角色照此办理）**

| 规矩 | 内容 |
|---|---|
| 锚点 | 一律沿用 `ax` / `ay`（脚底中心） |
| 尺寸 | 与现有 NPC **同规格** |
| 朝向 | **四向足够**，不做八向 |
| 站位 | **由数据算出来**，不手摆 |
| 待机 | **必须有**，不能是静止帧 |

> 后续谁做人物建模，**照这张表来**——不然拼到一张图上比例就乱了。

### 3.6 技术栈与运行

**① 数据层**

| 用途 | 选型 | 理由 |
|---|---|---|
| 骨架库 | `canteen.json` | 静态、量小、人工维护，**不需要数据库** |
| 口碑库 | `reviews.json` + `reviews_imported.json` | 每条自带六要素，纯 JSON 可读可查 |
| **内视图渲染** | **自己画**（Canvas 2D，见 §3.4）——**不调别人的地图 API** | 独立演示时没有校园大地图，内视图照样要出得来 |
| 校园图层（合体后） | 只输出"哪些窗口有口碑"的**数据**，谁去画不关我的事 | **是接口约定，不是实现依赖** |

**② 采集层（离线，一次性）**

| 用途 | 选型 | 理由 |
|---|---|---|
| 抓取 | Python + requests（**限速、只抓公开页**） | 离线跑，不进交付物 |
| 食堂相关性筛 | 关键词表（食堂 / 窗口 / 菜名 / 校内简称） | 先粗筛，再精抽 |
| **结构化抽取** | **LLM 离线批处理** | "今天学二三窗口的麻辣香锅排了二十分钟队但是真的香" → `{窗口: 学二三, 菜品: 麻辣香锅, 情感: +, 排队: 长}` |
| 清洗 | 去重 / 去广告 / 去个人信息 | 宁缺毋滥 |

**③ 检索与生成**

| 用途 | 选型 |
|---|---|
| 事实类（价格 / 时间 / 菜品） | **骨架库精确查**——不走向量，事实不需要模糊匹配 |
| 口碑类（好吃 / 排队） | **标签过滤 + 加权聚合** |
| 转述 | **自带 LLM 接入**（Key 与配置在本交付件内），**Prompt 里锁死她的口吻** |

**④ 可视化层**

| 用途 | 选型 | 理由 |
|---|---|---|
| 像素地图渲染 | **Canvas 2D** | 与校园地图同一套渲染方式，风格统一 |
| 底图缓存 | **离屏 Canvas 烘焙** | 底图静态，一次烘焙；每帧只重绘档口层 |
| 平面数据 | `canteen.json` 的 `floors[].stalls[].rect` | **格坐标**，与像素格对齐，缩放不糊 |
| 评分映射 | **5 档离散色阶** | 连续渐变在像素风里**糊成一团** |
| 标签布局 | 块内 → 引线外移 → 只留色块（**三级降级**） | 防重叠，**宁可少字不可叠字** |
| 交互热区 | 档口 `rect` 直接当热区，**不做额外命中检测** | 数据里已有矩形，拿来就用 |
| **人物渲染** | 精灵图 + 帧动画，**沿用地图的 `ax` / `ay` 锚点与 `baseY` 排序** | 与现有 NPC **必须同规格**，不然比例会乱 |
| **人物站位** | 由档口 `rect` **算出来**，不手摆 | 档口挪了，她跟着挪，不用重标 |

**⑤ 人格配置（设计文档 §5.6 留白处，此处填上）**

```json
{
  "id": "aunt",
  "name": "阿姨 · 丙",
  "role": "食堂窗口",
  "persona": "热络、絮叨、护短；管学生叫「孩子」；爱说「我跟你说」",
  "tools": ["getRating", "listWindows"],
  "roam": { "type": "static" },
  "unknown_line": "这个我真不知道，你问那个小向导去。"
}
```

**⑥ 运行形态**

| 项 | 内容 |
|---|---|
| 载体 | **与前端同体的 JSON 数据**——阿姨不引入后端，不引入运行时依赖 |
| 出现时间 | **只在饭点**（见设计文档 §13.3） |
| 主动性 | 三个老角色里**最活跃**的一个（见 §13.4） |
| **内视图** | 食堂两层像素地图（§2.5）——**进到食堂里才打开**，与她的饭点出现同源 |

### 3.7 与校园的挂接

> **本节写的全是「合体之后怎么接」**——隔离期这些都不存在，**我一个人也能跑**。

| 挂接点 | 内容 |
|---|---|
| **地图图层** | 有口碑的窗口在地图上高亮，点开看评分与评论 |
| **食堂内视图** | 两层档口像素地图（§2.5）——**这是我自己画的**，不是接别人的 |
| **饭点出现** | 只在饭点站在窗口后——**刷不出来她，只有走到食堂才见得到** |
| **主动性载体** | 她最活跃：路过食堂时她会主动搭话（不是推送，是**偶遇**） |
| **对外输出（合体后）** | 口碑数据可作为养成系统的反馈来源——**我只产出数据，接口留给对方**（接口约定，不是依赖） |

### 3.8 为什么这么选（答辩用）

**问：为什么爬校园墙，不爬大众点评？**

> 校园墙是**本校学生自己的公开言论**——它天然带校内语境（"学二""三窗口"这些简称），
> 第三方平台的评价不会这么写。**我们要的是校内人的真实体验，不是游客印象。**

**问：爬来的评价会不会污染口碑？**

> 底料带 `source: imported` 标记、走**更低权重**，且走**同一条衰减曲线**。
> 它是**垫脚石**：玩家贡献上来后自然淡出，**不需要人工清理**。

**问：为什么没有打分 UI？**

> **打分是说话的一部分，不是一次表单提交。**
> 玩家不需要知道"功能菜单在哪"——他只需要走到阿姨面前说一句"三窗口那个香锅真香"。

**问：为什么把口碑做成地图，而不是一张评分列表？**

> **列表要读，地图要看。**
> "学二哪个窗口好"这个问题，列表答一次只能答一个窗口；地图**一次答所有窗口**——
> 哪个红、哪个灰，扫一眼就知道，**连问都不用问**。
> 而且档口在图上的**位置**本身就是信息：**离门口近的窗口排队久**这种事，列表说不出来。

**问：为什么要两层，不能画一张大的？**

> 因为现实里**食堂就是两层**。两层塞进一张图，要么上下挤扁，要么玩家分不清自己在哪层。
> **两张平面图加一个切换按钮**，是最省事、也最不会看错的做法。
> **不做三维楼梯**——像素风里画三维室内，画不像、看不懂，还贵。

**问：为什么不用向量库 / 数据库？**

> 骨架库是**几十条**窗口记录，口碑库是**几千条**短评——这个量级下 JSON 直查比建索引快。
> **事实类问题走精确匹配，只有主观口碑才需要加权聚合。** 用不上的复杂度不加。

**问：为什么人物建模也归阿姨？**

> 因为**档口是她画的，站在档口后面的也得是她**。
> 两个人分头画场景和人物，比例、描边、配色必然对不上——**像素风里这种不统一一眼就能看出来**。

**问：为什么四向就够，不做八向？**

> 八向的斜向帧**要多画一倍**，玩家却**几乎注意不到区别**。
> 四向 + 一个像样的待机动画，**观感更好，成本更低**。

### 4.4 记忆隔离

**阿姨记得你吃过什么、说过什么，但其他角色不知道。**

**唯一例外是口碑公共层**——玩家贡献的评价会进公共层，被所有玩家看到（这是设计文档 §18 异步痕迹的一部分），**但对话内容、位置、私密记忆一律不进**。

> **隔离期的写法**：独立交付时，**公共层就是我自己的 `reviews.json`**——没有别人往里写，我也没往别处写。
> 合体时这份文件并入公共层，**我的代码一行不改**。

## 六、独立交付与合体接口

**本角色按隔离开发：数据与实现自包含，可独立开发、独立演示。**

**她是五个人里唯一的重交付**——其他人交的是「登录 + 聊天 + 本角色功能」，
她还要**自己把食堂和阿姨本人都画出来**。三块建模活全在她这儿。

### 6.1 交付件形态

**一个能独立跑起来的口碑应用**——登录进去，问哪个窗口好吃；或者直接把食堂的两层图打开看。

```
阿姨/
├── index.html          登录窗口 + 聊天界面（单页）
├── app/                口碑问答 / 加权聚合 / 内视图渲染
├── art/                美术（都是本文档自己画的）
│   ├── canteen/        食堂两层平面图（底图烘焙）
│   └── aunt/           阿姨的精灵图 + 动画帧
├── data/
│   ├── canteen.json    骨架库 + 两层平面（含 rect）
│   ├── reviews.json    口碑主流（玩家贡献的）
│   └── reviews_imported.json   底料（校园墙采的）
└── server/             账号服务
    └── main.py         FastAPI：注册 / 登录 / 签发 token
```

**怎么跑**：

```bash
pip install fastapi uvicorn
uvicorn server.main:app --port 8000
# 再打开 index.html
```

**答辩时怎么演**（两句话动线，她比别人多一句）：

> ① 打开页面 → 登录 → 问「三窗口的麻辣香锅值不值得排」→ 看她**带立场地**答；
> ② **直接打开食堂内视图** → 指着一层说「**哪个窗口红，一眼就看得出来**」，再切二层。

**账号服务**：**轻后端**（FastAPI + SQLite）——注册 / 登录 / 签发 token。
**它不是登录 UI 的附属，是「记忆归属」的前提**：有了 `user_id`，她记得你吃过什么，才能跨会话、跨设备挂在**同一个人**身上。
**本交付件自带一套，独立可跑**；合体时五套并成一套统一账号。

### 6.2 合体接口

| 项 | 内容 |
|---|---|
| **自包含** | 骨架库、口碑库、采集脚本、问答逻辑、**两层平面数据与内视图渲染**、**人物精灵与动画**——**全部在本角色内闭环**，不依赖其他角色的实现 |
| **唯一的外部约定** | ① 校园地图的**图层接口**与**内视图的进入约定**（点食堂 → 打开内视图）；② 行为层的**出现时间**（饭点）——**都是接口约定，不是实现依赖** |
| **合体方式** | ① 按总体设计 §2.2 的「工具集 + 人格配置」接入，对外暴露 `getRating()` / `listWindows()`；② 内视图作为**可挂载组件**暴露（给它一个容器和 `canteenId` 就能渲染） |
| **合体后** | 引擎读 `tools` 知道她会干什么、读 `persona` 知道她怎么说话——**引擎一行不改** |
