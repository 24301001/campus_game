# 算法哥 · 角色功能与实现

| 项 | 内容 |
|---|---|
| 角色 | 算法哥（**新角色**，第五个智能体） |
| 定位 | **竞赛刷题 · 在线判题 · 学情教练型智能体** |
| 对标 | 与「学霸哥」相对——学霸哥管课业考试，算法哥管竞赛刷题 |
| 底座 | **已完整实现的仿 LeetCode 判题平台**（功能对标 LeetCode 全量） |
| 版本 | v1.0 · 2026-09-18 |

---

## 一、一句话定位

**校园里那个天天泡在 OJ 上、能把你的代码从 WA 讲到 AC 的人，也是那个记得你每道题是怎么错的教练。**

他和学霸哥是**一对**：学霸哥是「卷绩点的」，算法哥是「打比赛的」。两个人都懂技术，但走的路完全不同——**学霸哥给你讲原理，算法哥让你把代码交上去真跑一遍。**

---

## 二、功能清单

### 2.1 题库与刷题（核心）

**他能给你什么题**——按知识点、难度、标签组织：

| 维度 | 分类 |
|---|---|
| **难度** | 简单 / 中等 / 困难 |
| **标签** | 数组、字符串、哈希、双指针、滑动窗口、二分、栈与队列、链表、二叉树、图论、回溯、贪心、动态规划、并查集、位运算、数学…… |
| **来源** | 竞赛真题、面试高频、教材配套习题 |
| **每日一题** | 每天一题，做完可拿猫粮（见 §3.4） |

**输出要求**：
- 题面**完整**——描述、示例、数据范围、时间/空间限制
- **相似题推荐**——做完一道，推同类型的下一道（见 §3.3）
- **不会做能问**——不是丢给你一道就走

### 2.2 在线判题（真编译 · 真执行 · 真用例）

**这是他的看家本事，也是和学霸哥最大的区别：学霸哥讲得对，算法哥判得准。**

| 环节 | 内容 |
|---|---|
| **提交** | 编辑器里写完 → 提交 → 真实编译、真实执行 |
| **结果** | AC / WA / TLE / MLE / RE / CE / OLE，逐用例反馈 |
| **用例** | 样例公开 + **隐藏用例**（防硬编码骗分） |
| **性能** | 每个用例的**用时与内存**、最慢用例、**击败百分比** |
| **试跑** | 支持自定输入本地运行（Run），不必等提交 |
| **多语言** | 一门语言的题面，多门语言都能交 |

**输出要求**：
- **错了要告诉他为什么错**——给反例（哪组输入错了）、给方向（超时？边界？溢出？）
- **对了也有话说**——用时排在什么位置、有没有更优解法
- **不是冰冷的红绿**——判题结果是算法哥讲的，不是页面上一个叉

### 2.3 分级提示（不给答案，给路）

**和学霸哥的解题辅导是同一个设计：一步都不许跳。**

| 级别 | 给什么 |
|---|---|
| **L1 方向** | 这题是什么类型、往哪个方向想 |
| **L2 步骤** | 关键一步是什么、为什么这么想 |
| **L3 伪代码** | 完整思路的骨架，但还不能直接交 |
| **L4 完整代码** | 只在前面都走完了才给 |

**输出要求**：
- **默认从 L1 开始**，卡住了再要下一级
- **可以直说"我不会"**——那就回到 L2，把关键步骤讲透
- **目标不是让你抄过**，是让你下一次能自己写出来

### 2.4 刷题记录（一切分析的原料）

| 记录什么 | 内容 |
|---|---|
| **提交** | 每次提交的代码、语言、结果、逐用例用时与内存 |
| **过程** | 打开过哪些题、提交几次才过、用了哪一档提示 |
| **时间** | 每次提交的时刻 → 做题日历（热力图）、连续天数、活跃时段 |
| **生涯汇总** | 四年刷了多少题、AC 率多少、最长连续多少天（接「生涯记录」） |

**输出要求**：
- **不是流水账**——每条记录都要能被后面的分析用上
- **可回看**——"我上周那道题当时怎么写的"能翻出来

### 2.5 学情分析与指导（**他的大脑**）

**拿全量记录做系统性诊断，然后开处方。**

| 分析维度 | 看什么 | 给出什么结论 |
|---|---|---|
| **标签画像** | 每个标签的题数与通过率 | 哪类题稳、哪类题虚 |
| **难度画像** | 简单/中等/困难的分布与卡点 | 能力边界卡在哪一档 |
| **错误归因** | WA / TLE / RE / CE 的分布 | **不是"你错了"，是"你错在哪一类"** |
| **进步曲线** | 通过率随时间的变化 | 在进步，还是在原地打转 |
| **习惯画像** | 活跃时段、连续天数、单题耗时 | 刷得多，还是刷得巧 |
| **同行坐标** | 与全局榜单在同题、同标签上的对比 | 这题上你比多少人强 |

**错误归因是这一节的灵魂**（也是最难的一块）：

| 症状 | 归因 | 处方 |
|---|---|---|
| WA 集中在边界输入 | 边界条件没考虑 | 专练「边界与特判」类题 |
| TLE 集中在数据规模大的题 | **复杂度选错了** | 回头补复杂度分析 + 换算法的题 |
| RE 多 | 数组越界 / 空指针 / 递归爆栈 | 基础功课题 |
| 同一题反复 WA | 没读懂题就动手 | 先写思路再写代码 |

**输出要求**：
- **给结论，不是给数据**——"你 DP 标签 12 题过了 4 题，其中 5 次 TLE ⇒ **是复杂度估算的问题，不是思路问题**"
- **每条结论都要能落到一个动作**——不能只诊断不治疗

### 2.6 题单推荐（**把指导变成计划**）

**不是"再给你一道题"，是一份按你情况排好的计划。**

| 输入 | 内容 |
|---|---|
| **你的画像** | §2.5 的诊断结果 |
| **你的目标** | 备赛 / 面试 / 补短板 / 保持手感 |
| **你的预算** | 每天几题、练到哪天 |

| 输出 | 内容 |
|---|---|
| **有序题单** | 第 1 天做什么、第 2 天做什么，难度递进 |
| **选题目径** | 薄弱标签加权 + 知识点依赖拓扑 + 排除已做 + 难度不跳档 |
| **可解释** | 每题给一句入选理由——"为什么给我这道" |
| **是活的** | 做完一天自动重算，不合适的可换 |

**和 LeetCode Study Plan 的区别（答辩必答）**：

> LeetCode 的 Study Plan 是**人工预设**的，全世界同一个顺序。
> 算法哥的题单**按你的记录动态生成**——**同一个班两个人，拿到的题单不一样。**
>
> **平台给你数据，算法哥给你结论和下一步。**

### 2.7 竞赛与排名（全局榜单）

| 功能 | 内容 |
|---|---|
| **榜单** | 做题数 / 通过率 / Rating 排名 |
| **范围** | **全局榜**——跨会话、跨玩家 |
| **告诉你排名** | 你在第几、离上一名差几题、本周升了几名 |
| **分标签排名** | "你 DP 排 210、图论排 88"——**比总排名更有指导意义** |
| **比赛** | 定时赛、排行榜、赛后复盘 |

**⚠️ 榜单口径（必须写死的边界）**：
**榜的是学习数据，不是人。** 题数、通过率、Rating 上榜；
**对话内容、位置、私密记忆一律不上榜**——这是单机模式 50 会话隔离的底线。

### 2.8 校园信息问答

**不做。** 他的舞台是竞赛与代码，校园琐事归其他角色（见 §四）。

## 三、实现方案

### 3.1 平台底座（已完整实现，不重造）

**判题平台是现成的**，功能对标 LeetCode 全量，本节不重复造轮子，只列账：

| 模块 | 能力 | 状态 |
|---|---|---|
| 题库 | 题目列表 / 难度 / 标签 / 相似题 / 每日一题 | ✅ 已有 |
| 题面 | 描述 / 示例 / 约束 / 提示 | ✅ 已有 |
| 编辑器 | 语法高亮 / 自动补全 / 多语言 / 自定输入试跑 | ✅ 已有 |
| 判题 | 编译 / 执行 / 逐用例 / 隐藏用例 / 状态机 | ✅ 已有 |
| 沙箱 | 资源限制（时间·内存·进程·输出） | ✅ 已有 |
| 性能 | 逐用例用时内存 / 击败百分比 | ✅ 已有 |
| 题解与讨论 | 官方题解 / 社区题解 / 讨论区 | ✅ 已有 |
| 竞赛 | 定时赛 / Rating / 排行榜 / 虚拟参赛 | ✅ 已有 |
| 学习 | 学习计划 / 探索卡片 / 分类 | ✅ 已有 |
| 个人 | 主页 / 提交历史 / 做题日历 / 收藏 / 笔记 | ✅ 已有 |
| 社交 | 关注 / 好友 / 排行榜 | ✅ 已有 |
| 积分 | 签到 / 积分 | ✅ 已有 |
| 面试 | 模拟面试 / 面试题集 | ✅ 已有 |
| Playground | 代码沙盒 | ✅ 已有 |

> **一句话**：**功能齐了，缺的是「人」。** 下面三节全是角色层的新工作。
> **平台给你数据，算法哥给你结论和下一步。**

### 3.2 判题链路（跑在平台里，这里只说清口径）

```
代码提交 → 队列 → 判题 worker → 沙箱内编译
        → 逐用例执行（限时·限内存）
        → 比对输出（多解题走特判 SPJ）
        → 汇总：AC / WA / TLE / MLE / RE / CE / OLE
        → 计时计存 → 与基准库比对给出击败百分比
```

**四条口径**（答辩容易被追问）：

| 问题 | 口径 |
|---|---|
| 怎么防硬编码骗分？ | **隐藏用例**——样例公开，判分用另一套 |
| 怎么防"超时了但悄悄过了"？ | 受限时**墙钟 + CPU 时间**双约束，卡死即 TLE |
| 多解题怎么办？ | **特判（SPJ）**——不比对固定输出，跑校验程序 |
| 怎么防提交恶意代码？ | 沙箱隔离：限进程数、限输出、限文件系统 |

### 3.3 智能体层（**角色的价值全在这**）

**平台是工具，算法哥是会用工具的人。** 这一层是平台上没有的：

| 能力 | 怎么实现 |
|---|---|
| **分级提示 L1→L4** | LLM 多轮对话，**每级提示前先检索题解与相似题**，让它讲得像人解题而不是背书 |
| **相似题推荐** | 检索层（BM25 + 向量 + RRF + 重排）把"题目描述"当查询串 |
| **判题结果人格化播报** | 结果状态机 → 模板 + LLM 包装：WA 给反例与方向、TLE 给复杂度分析、AC 给性能点评 |
| **学情分析引擎** | 全量提交记录 → 标签/难度画像 + **错误类型归因**（WA/TLE/RE/CE 分布）→ 输出结论而非数据 |
| **题单生成器** | 画像 + 目标 + 预算 → 知识点依赖 DAG 拓扑 + 薄弱标签加权 + 排除已做 + 难度不跳档 → **有序、可解释、可重算**的题单 |
| **排名播报** | 总榜 + 分标签榜 → "你离上一名差几题、本周升了几名" |

**关键设计：判题不经过 LLM。**

> **判题是确定性的**（编译器 + 沙箱 + 用例），**LLM 只负责讲思路**。
> **该确定的地方用确定性，该智能的地方用智能。**

**这一条是算法哥的技术底色**——判题结果不可被幻觉篡改，讲解才允许发挥。

### 3.4 技术栈与运行

**分五层，各层选型如下。**

**① 前端（长在像素校园里）**

| 用途 | 选型 | 理由 |
|---|---|---|
| 代码编辑器 | **Monaco Editor** | VS Code 的内核、LeetCode 同款；高亮 / 补全 / 多光标 / 缩进全现成，**不自己写编辑器** |
| 题面渲染 | Markdown + **KaTeX** | 题面里的公式、代码块、表格要能正常渲染 |
| 结果展示 | 逐用例表格 + 用时/内存条形对比 | 让"击败 x%"**看得见** |
| 通信 | HTTP + 提交后 SSE/轮询取结果 | 判题是**异步**的，不能同步阻塞等 |

**② 后端服务**

| 用途 | 选型 | 理由 |
|---|---|---|
| API 服务 | **FastAPI**（或 Node/Fastify） | 只做收提交、发题面、给榜单；**与判题 worker 解耦** |
| 任务队列 | **Redis**（List / Stream） | 提交进队、worker 出队——**削峰**，防止判题机被打爆 |
| 判题 worker | **Go / Python** 多进程池 | 独立可伸缩，判题机**横向加机器**即可扩容 |
| 数据库 | **PostgreSQL** | 题库 / 提交 / 进度；关系型**算得清**"知识点通过率"这类聚合 |
| 榜单 | **Redis Sorted Set** | 排行榜的标准做法：O(log N) 更新与取区间 |

**③ 判题沙箱（唯一需要"重"的地方）**

| 用途 | 选型 | 理由 |
|---|---|---|
| 容器隔离 | **Docker**，每语言一个镜像 | 语言环境互不污染 |
| 进程隔离 | **isolate**（IOI/ICPC 标准）或 **nsjail** | 业界判题标准工具，**不是自己糊的沙箱** |
| 资源限制 | **cgroup v2 + seccomp** | 限 CPU 时间、内存、进程数、输出大小 |
| 判题协议参考 | **Judge0** / **HydroOJ** / **DOMjudge** | 成熟实现，不必从零造判题轮子 |
| 语言镜像 | gcc/g++ · python3 · openjdk · node · go | 一门语言一个镜像，提交时选 |

**④ 智能体层**

| 用途 | 选型 |
|---|---|
| 检索（相似题 / 题解） | **BM25 倒排 + 向量余弦（bge-m3 / Qwen3-Embedding）+ RRF 融合 + bge-reranker 精排** |
| 生成（分级提示 / 判题播报） | **自带 LLM 接入**（Key 与配置在本交付件内） |
| 学情分析 | **SQL 聚合出画像**（确定性）+ LLM 做归因表述（智能） |
| 题单生成 | **知识点 DAG 拓扑排序 + 加权打分**（可解释），LLM 只负责写入选理由 |

**⑤ 运行与部署**

| 项 | 内容 |
|---|---|
| 部署形态 | **Docker Compose** 一键起：`api + worker + postgres + redis` |
| 演示形态 | 判题服务与前端分离——**前端仍是那份单文件 HTML** |
| 基准库 | 每题跑一遍参考实现，存下参考用时与内存——**"击败百分比"由此而来** |

> **一句口径**：**该重的地方重（判题沙箱），该轻的地方轻（前端仍是纯前端零依赖）。**

### 3.5 与校园的挂接（让它是个人，不是个网页）

| 挂接点 | 内容 |
|---|---|
| **题单 → 每日任务** | 题单的一天 = 当天的任务——**把"今天做什么"交给算法哥** |
| **刷题 → 奖励事件** | 每日一题、AC 一题 → **产生一次奖励事件**（合体后由养成系统发放）——**学习是唯一稳定货币来源** |
| **生涯记录** | 刷题数、AC 率、连续天数汇入「大学四年回看」 |
| **能力画像** | 知识点掌握度 → 影响宠物属性成长方向 |
| **主动性载体** | 比赛开赛**不推送**——算法哥到点在某个地点等你（与保安巡逻同源，见设计文档 §13） |
| **物理载体** | 他在机房里、在图书馆的电脑区、在教学楼——**走到他面前才说话** |

**为什么必须挂接**：**只做一个 OJ 网页，它就只是个 iframe。** 挂上经济、生涯、主动性这三条，它才是校园里的一个人。

### 3.6 为什么这么选（答辩用）

**问：为什么不在浏览器里跑判题沙箱？**

> 判题需要**真实的编译与执行环境**、**严格的资源隔离**、**不可绕过的时限与内存限制**。
> 浏览器里做不到真正的隔离与限时——**判题必须跑在能限制它的地方。**
>
> 我们**只在必须的地方引入后端**：地图、问答、口碑、失物**全部仍是纯前端零依赖**，
> **后端只服务判题这一件事。**

**问：为什么题解和讨论区还在？不是有算法哥了吗？**

> 题解与讨论是**沉淀**，算法哥是**对话**。要按需检索去翻题解，要一步步被问到会就找算法哥。
> **两种学习的姿势，都要有。**

**问：LeetCode 也有 Study Plan，你们和它有什么区别？**

> 它是**人工预设**的，全世界同一个顺序；算法哥的题单是**按你的记录动态生成**的——
> **同一个班两个人，拿到的题单不一样。**
> **平台给你数据，算法哥给你结论和下一步。**

**问：判题结果为什么不让 LLM 直接判？**

> **判题是确定性的，不能被幻觉篡改。** 编译器说 CE 就是 CE，用例说 WA 就是 WA。
> LLM 只做它擅长的：**把结果讲成人话、把思路拆成台阶。**

## 四、边界

### 4.1 与学霸哥

| | 算法哥 | 学霸哥 |
|---|---|---|
| 主题 | 竞赛、刷题 | 课业、考试、课本 |
| 形态 | 出题、判题、看代码 | 讲原理、给资料、解推导题 |
| **分界** | **能提交代码判分的找他** | **要讲原理、要资料、要一步步推导的找他** |

**重叠区处理**：数据结构大作业这种既是课业又是算法的——
- **交代码判分的部分 → 算法哥**
- **写报告、讲原理的部分 → 学霸哥**

### 4.2 与其他角色

| 角色 | 分工 |
|---|---|
| 向导 · 小北 | 他管**空间**（在哪、怎么去），算法哥管**代码**（对不对、快不快） |
| 阿姨 · 丙 | 阿姨管**吃**，算法哥管**做** |
| 保安 · 老丁 | 无重叠 |

### 4.3 记忆隔离

**算法哥记得你交过什么代码、卡在哪一档提示，但其他角色不知道。**

**唯一例外是榜单**——全局榜共享**学习数据**（题数 / 通过率 / Rating），
**对话、位置、私密记忆一律不共享**。这条边界要写死在文档里。

## 六、独立交付与合体接口

**本角色按隔离开发：技术栈自包含，可独立开发、独立部署、独立演示。**

### 6.1 交付件形态

**一个能独立跑起来的刷题应用**——登录进去，写代码，看判题，看榜单。

```
算法哥/
├── index.html          登录窗口 + 聊天界面（单页）
├── app/                前端：题库 / Monaco 编辑器 / 榜单
├── server/             后端（FastAPI）
│   ├── auth.py         账号：注册 / 登录 / 签发 token
│   ├── judge.py        判题队列 + 沙箱调度
│   └── users.db        SQLite
├── sandbox/            判题沙箱（Docker + isolate）
└── data/               题库与测试用例
```

**怎么跑**：

```bash
docker compose up -d      # 沙箱 + 后端
# 再打开 index.html
```

**答辩时怎么演**（一句话动线）：

> 打开页面 → 登录 → **粘一段错代码提交** → 看它判 WA 并**指出错在哪类用例上** → 再看全局榜单上有没有自己。

**账号服务**：**轻后端**（FastAPI + SQLite）——**并入已有的判题后端，不另起服务**。
**它不是登录 UI 的附属，是「记忆归属」的前提**：有了 `user_id`，刷题记录才能跨会话挂在**同一个人**身上。
**本交付件自带一套，独立可跑**；合体时五套并成一套统一账号。

> **榜单尤其吃这条**：榜上的每一行都是一个 `user_id`——**没有账号，就没有榜单**。

### 6.2 合体接口

| 项 | 内容 |
|---|---|
| **自包含** | 判题平台、后端服务、检索层、学情分析——**全部在本角色内闭环**，不依赖其他角色的实现 |
| **唯一的外部约定** | ① 地图的**挂点接口**（算法哥站哪）；② 合体后**奖励事件的投递约定**——**我只发"该发猫粮了"这个事件，谁来发不关我的事**。两者都是接口约定，不是实现依赖 |
| **合体方式** | 按总体设计 §2.2 的「工具集 + 人格配置」接入，对外暴露 `submitCode()` / `getRank()` / `analyzeProgress()` / `makePlan()` |
| **合体后** | 引擎读 `tools` 知道他会干什么、读 `persona` 知道他怎么说话——**引擎一行不改** |
